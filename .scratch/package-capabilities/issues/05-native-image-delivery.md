# Measure native image delivery and move asset reads off the command executor

Status: ready-for-agent
Type: task
Blocked by: none

## Outcome and scope

Measure native editor image loading, then compare the existing data-URL command with the same operation on a blocking worker. Keep the current image contract, vault containment, document-owned cache and pane-owned interactions. The ready scope is the measurement harness, minimal worker experiment and evidence-backed decision. A native asset-protocol transport is a **conditional follow-up design**, not a fully specified implementation authorized by this ticket's ready status. This ticket plans work; no measurements or implementation have yet been performed.

This follows the [capability investigation](../../../docs/research/upgraded-package-capabilities-2026-10-21.md#2-image-delivery-promising-measure-first-medium-effort). The feature does not require adopting a new protocol to obtain the immediate scheduling improvement. Tauri 2.12.5 has asynchronous asset handling, but this application currently serves editor images through its own commands.

## Current owners and constraints

- Native commands: `src-tauri/src/commands/asset_commands.rs`. `read_image_asset_data_url` synchronously derives the Running Vault assets directory, canonicalizes the reference, reads bytes and returns `data:<extension-derived MIME>;base64,<STANDARD encoding>`. `read_image_asset_fingerprint` synchronously returns `<byte length>:<modified nanoseconds>`. `store_pasted_image` owns exclusive-create imports and is outside the first read-only experiment.
- Dispatch seam: `src-tauri/src/commands.rs::on_app_worker` already obtains AppState inside a per-invocation blocking task. It is not a global serialized worker. Reuse it from the child command module; retain both outer dispatch and inner command error results, then flatten to the existing `Result<String, String>` contract. Change read commands to async wrappers accepting an owned generic AppHandle, rather than moving a borrowed State across an await. Do not add another application worker abstraction.
- Containment: `src-tauri/src/asset_paths.rs::resolve_asset_image_path` permits contained relative subfolders and rejects absolute paths, traversal, backslash/colon forms and canonical symlink escapes. Keep this shared rendering/indexing seam; converting a path to a URL cannot grant access. Preserve existing behavior rather than claiming canonicalization eliminates every adversarial filesystem race.
- Shared frontend resource: `src/lib/features/notepad/editor/editorDocumentResources.ts` constructs the document's loader; `src/lib/features/notepad/images/imageAssetLoader.ts` coalesces requests, keys by root plus name, checks fingerprints and evicts by 128 entries / 24 MiB of URL-string length. This existing accounting is a string budget, not a bound on WebView decoded image memory.
- Generation retirement prevents late results from repopulating the cache after `destroy()`. A pending promise may still settle to its original caller: preserve the caller/view lifetime rejection already required by image interactions; do not claim destroy cancels native I/O.
- `src-tauri/src/commands/media_search.rs` already runs thumbnail and image-query decoding on `on_app_worker`. `src-tauri/src/semantic/image_input.rs` has a separate PNG/JPEG/static-WebP policy, byte/pixel/allocation bounds and EXIF/alpha preprocessing. Editor embeds support a broader MIME set. Do not apply the semantic decoder's narrower format policy to editor display.
- `src-tauri/Cargo.toml` does not enable Tauri's asset-protocol feature; `src-tauri/tauri.conf.json` allows asset URLs in CSP but does not configure a permitted asset root. An existing CSP entry is insufficient to make that path work.

Read [architecture](../../../ARCHITECTURE.md#images), [image invariants](../../../docs/architecture/behavior-invariants.md#image-interactions) and [Running Vault invariants](../../../docs/architecture/behavior-invariants.md#vault-selection-applies-on-the-next-launch). Assets remain bound to the immutable Running Vault until a new process starts. Staging a Next-launch Vault Selection must not redirect reads or mutate caches to the staged root. Retained views do not share DOM or gesture state. Deleting an embed must not delete bytes. Clipboard imports preserve selection until success and reject results from retired views.

## Stage A — reproducible baseline and bounded worker experiment

1. Add a focused, opt-in native image-delivery measurement next to `e2e/specs/native/image-interactions.spec.ts`, using the existing pinned-binary/disposable-vault native launcher. Generate deterministic fixtures into the disposable vault: small icons, medium compressed photographs, a few large compressed images, repeated references and distinct images exceeding the existing cache budget. Include encoded spaces/Unicode and a nested asset path. Record actual fixture hashes, encoded sizes and decoded dimensions. Do not import private user images or change format/size admission policy.
2. Record manifest/package versions, binary hash, OS/CPU/architecture, build profile, scale factor, fixture metadata and revision. Compare the same build profile and machine; a debug-before/release-after comparison is invalid. Use at least ten measured invocations per representative cold-application-cache case and warm-cache case after warm-up, alternate baseline/variant order, and save samples plus median/p95. A cleared application cache does not establish a cold OS page cache; label that distinction.
3. Measure independently: command duration and bytes returned, note navigation to image `load`/decode completion, warm fingerprint-only checks, cache re-reads/evictions, retained/peak native and WebView memory where observable, and input responsiveness during a burst of asset reads. Use explicit image-ready signals rather than sleeps. Timestamp JS frame gaps and a harmless loopback IPC probe under load; when attributing blocking to the native executor, capture native main-thread/worker scheduling evidence too. Neither image decoding nor paint completion follows merely from a fulfilled command. Any instrumentation belongs to the opt-in test/debug seam, with no release logging of vault paths or image data.
4. Convert **both** read commands to `on_app_worker` wrappers. Keep filesystem access, containment, metadata lookup and encoding inside the blocking operation, and derive the Running Vault path from AppState there. Preserve command names, `fileName` argument, fingerprint representation, MIME selection, returned bytes and normal command errors. Frontend loader APIs and configuration remain unchanged. Do not change paste writes, native initialization, shutdown coordination or command registrations unless compilation requires a narrowly mechanical signature adjustment.
5. Repeat the same native workload. Test concurrent same-name/multiple-name reads; retain frontend coalescing rather than adding a second backend cache. Verify that worker placement does not create unbounded application queues or materially worsen memory under the finite burst fixture. If that occurs, record it as a design question before adding new concurrency ownership.

### Decision rule and rollback

Record the rule before measuring: prefer the smaller worker variant if scheduling evidence shows filesystem/encoding work moved away from native command execution, functional gates pass, and representative p95 image-ready/IPC-probe latency and memory do not regress beyond observed repeat-run variation. Treat a persistent regression over 10% as a stop requiring explanation and a rerun; this is an experiment guard, not a universal product SLA. If baseline responsiveness has no measurable problem, say so rather than claiming a speedup from architectural reasoning alone.

Keep scalar baseline and worker changes separately reviewable. If the worker experiment fails correctness or shows a repeatable unexplained regression, revert only its command wrappers and experimental runtime changes, retain the evidence and fixtures, and leave the current transport in place. Do not compensate for unfavorable results by widening scope, weakening bounds, increasing permissions or changing unrelated image behavior.

## Nested alternative — base64 SIMD, only if encoding remains material

Run this within the same measurement effort, after isolating encode time from disk, IPC copies and WebView decode. It is not a separate product feature or a reason to rewrite every base64 call site.

- Installed base64 0.23.1 defaults include `std` and `simd-unsafe`, but the app explicitly selects scalar `general_purpose::STANDARD`. Where supported, compare a cached runtime-selected `base64::engine::simd::Simd::standard(GeneralPurposeConfig::new())` with that scalar engine. Construct/select once rather than on every small encoding. Use cfg-gated fallback for architectures where the `Simd` type is unavailable: published source gates it to x86_64/aarch64 with `std`. Runtime fallback on these architectures does not make the type available on all other targets.
- Preserve standard `+`/`/` alphabet and canonical `=` padding exactly; the current `AAECAw==` fixture must remain identical. Cover empty input; lengths modulo three; vector-threshold boundaries; all byte values; small icons and realistic image sizes. Runtime detection must be used; do not call unchecked AVX2/NEON constructors or impose a CPU requirement. Exercise scalar fallback and compile-check actual supported desktop/mobile targets where toolchains are available; explicitly record unavailable cross-target validation.
- Start with encoding for editor data URLs only. Do not opportunistically replace note-timeline `URL_SAFE_NO_PAD` IDs. Thumbnail encoding is a later candidate only with independent evidence because those payloads are small. If image-query decode is ever included, preserve strict invalid-alphabet, malformed-padding, trailing-bit and byte-limit rejection and user-facing error categories; encoding parity alone does not prove decoder compatibility.
- Adopt only if end-to-end evidence shows a useful improvement beyond run variation; a large isolated throughput improvement with unchanged image-ready time is insufficient on its own. Otherwise document that no engine change is warranted. SIMD does not remove base64 expansion or IPC/JS string copies.

Published primary source: [base64 0.23.1 SIMD engine](https://docs.rs/crate/base64/0.23.1/source/src/engine/simd.rs) and [feature configuration](https://docs.rs/crate/base64/0.23.1/source/Cargo.toml).

## Stage B gate — decide whether scoped native asset delivery merits a design

Consider this only if Stage A identifies IPC string copies/base64 expansion as a material remaining cost (for example a repeatable memory or readiness bottleneck in image-heavy notes). Save an explicit keep-data-URL / design-protocol decision with evidence. If worker delivery is sufficient, close this ticket after Stage A without manufacturing a transport migration.

Before implementing any protocol variant, amend this issue or create its linked child implementation issue with the following resolved choices; that later implementation remains `needs-triage` until they are specified:

1. Choose built-in asset protocol versus a named asynchronous custom handler. Check installed Tauri implementation, feature gates and supported desktop/mobile targets. Built-in scope checks must be demonstrated to enforce our contained relative-image policy, including canonical symlinks, rather than assumed equivalent to `asset_paths.rs`. A custom handler must reuse that policy on every request and keep its root fixed to the Running Vault. Never allow the entire filesystem, a staged next-launch root or arbitrary client-supplied absolute paths.
2. Define bootstrap ownership and scope installation before first use. Scope only the canonical assets root, no recursive parent grant. Decide whether known contained symlinks remain supported and how replaced/deleted files are admitted. Specify response MIME, SVG handling, missing/denied responses, URL encoding and cross-platform origin behavior. The current extension-derived MIME behavior differs from Tauri's magic-byte MIME detection; prove compatibility rather than silently changing which image bytes WebView executes/displays.
3. Define freshness explicitly: fingerprint cache-busting/versioning, a file change between metadata read and delivery, invalidation on reload, browser HTTP caching and negative results. The `<length>:<mtime>` fingerprint is the existing policy, not a cryptographic content identity. Preserve same-size/mtime limitations unless a separately justified contract change is approved.
4. Define URL and memory lifetime under document destruction, pane replacement and process restart. URL-string length ceases to approximate cached image bytes after switching transport; specify replacement cache accounting and prevent old URL objects/results from authorizing later roots. Browser decoded-resource caches need separate observation. Do not add a second vault root owner in the frontend or make per-pane URLs own shared bytes.
5. Retain a data-URL fallback until all native acceptance passes. Specify how to turn the protocol path off without rewriting authored Markdown or losing images. New protocol permissions/CSP changes need a narrowly scoped reviewed diff and packaged-build verification; dev acceptance alone cannot establish production CSP success.

Primary source: [Tauri 2.12.5 asset handler](https://docs.rs/crate/tauri/2.12.5/source/src/protocol/asset.rs). The installed source uses spawned asynchronous handling and filesystem reads; that says nothing about this application's current command path or an unmeasured speedup.

## Verification and acceptance

- Focused Rust helper tests retain exact encoded payload/MIME behavior and cover missing paths, nested local paths, absolute/traversal/backslash/colon rejection and symlink escape. Verify async wrapper invocation and safe error propagation through actual native IPC. Preserve exclusive-create paste/import tests unchanged.
- Existing `imageAssetLoader.test.ts` must still prove coalescing, root separation, fingerprint refresh, retry, entry/byte eviction and no stale retention after disposal. Add a race test only for a behavior changed by implementation; do not rewrite this cache as part of the worker experiment.
- Run browser image interactions and split inventory coverage for pane-local selection/viewer behavior. Native `image-interactions.spec.ts` must still import, show, resize, reopen, cut and undo while retaining asset bytes. Extend native fixture acceptance for staging a second Next-launch Vault Selection: reads remain in the current Running Vault; an actual fresh process binds the staged vault without reusing prior resources. Use only launcher-owned disposable folders.
- Use [UI verification](../../../docs/agents/ui-verification.md) for interactive sessions/export/replay and retain meaningful screenshots/traces. Native measurements requiring real input, focus or paint use the explicit foreground lane under [E2E conventions](../../../e2e/README.md); background tests cannot establish those claims. Coordinate that lane serially with other native checks and benchmarks. Stop only owned servers/processes and remove disposable fixtures.
- Record results, limits and the transport decision in one evidence report under this feature's evidence directory, retaining selected machine-readable samples and reproducible fixture generation. Report separately what passed functional checks, what was measured, and what could not be validated. Existing native pane-width baseline failures are unrelated and must not be silently absorbed or fixed by this ticket.
- Complete the ready scope when the baseline/worker comparison, relevant correctness checks, optional SIMD decision and Stage B go/no-go are reviewable. A justified decision to retain data URLs is a successful outcome. Do not claim the protocol is implemented by resolving Stage A.

## Parallel work and ownership collisions

The Stage A command pair/helper tests and a new opt-in image-specific fixture can be developed independently of connection classification (01), search excerpts (06) and render recovery (04). They share AppState/IPC and native acceptance, so avoid editing `commands.rs`, `lib.rs`, shared native launcher/config or broad test bridges unless the integration owner coordinates the change. The existing `on_app_worker` needs no modification for this ticket. Stage B may touch `src-tauri/Cargo.toml`, Tauri config, bootstrap composition and `editorDocumentResources.ts`; reserve those changes until its design gate and coordinate with the render-recovery owner. Bench infrastructure work may proceed in parallel, but native performance sampling must run alone; baseline metadata can later use the common reporting format without blocking initial fixtures.
