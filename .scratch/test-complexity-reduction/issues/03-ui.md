## Recommended implementation

### A. Remove Settings' redundant loader layer and its parallel mocking layer

Files: `src/lib/features/settings/loaders/{forgottenLoader,settingsViewLoader,vaultLoader}.ts`, `store.svelte.ts`, `store.test.ts`; move only the SettingsViewPayload DTO to the existing store module (type-only consumers update), not another new loader/helper file.

All three loader modules have exactly one production consumer, SettingsStore. They only rename commands, add a constant page size, or wrap the existing history command normalizer. There is no independent lifecycle or admission policy. Current Settings tests mock both the native IPC boundary AND two of these intermediate modules, with four independent slice spies, separate resetting and default setup. This prevents normal store tests from exercising actual list/page command names and history error normalization.

Delete the three modules (23 + 20 + 13 current baseline lines), inline their six native calls in the store, preserve `invokeHistoryCommand` for Missing Notes/page errors, preserve page limit 30, and keep historyLoader: it has other consumers and explicit destructive confirmation. Keep one existing `invokeMock` with command-aware responses in tests; remove both loader `vi.mock` registrations and all four parallel slice spies. Use simple per-test command response values/deferred promises rather than another exported fixture framework. Existing race/action tests continue to invoke the same production store; expectations move from internal slice calls to command names/args.

Retained coverage owners: every existing Settings lifecycle, stale success/error, pending write/action, Missing pagination, forgotten mutation, typed history failure and vault staging test remains. IPC/History contract suites remain distinct. This change reduces production adapter names and test interception seams, not merely file placement.

Risk: response ordering in tests currently relying on blanket `invokeMock.mockResolvedValue` must become command-aware so a mutation response cannot accidentally serve a subsequent list query. Verify every command path involved in the retained tests, especially bundled view rejection (no fallback) and history normalization. Estimate: net 40–80 production/setup LOC reduction; two mocked-module concepts and four spy/reset concepts removed.

### B. Delete dead semantic presentation API and duplicate retry predicate tests

Files: `settings/semanticStatus.ts`, `settings/semanticStatus.test.ts`, `settings/SemanticSettingsPanel.svelte.test.ts`.

`rg` confirms `semanticStatusLabel` has **zero production callers**; only its test uses it. Delete that function and its health-label test. Inline the one-expression `shouldShowSemanticRetry` predicate at its only production caller, searchReadiness, and remove its separate export/test. Delete the now-empty semanticStatus.test.ts (47 lines). Keep all existing readiness and SSR branches. Add `retryExhausted: true` with otherwise fresh health to the existing “offers recovery or resume only when needed” readiness test, preserving the sole distinct predicate case. Fresh/nonretry and degraded cases already exist in that file.

This removes a dead parallel presentation model and an unnecessary production interface. Expected reduction: approximately 65–70 LOC and one test file; no rendered status behavior removed. No new test case count is required.

### D. Delete duplicate chat orchestration cases and fold the callback assertion into its real completion scenario

Retained owner: `controller.lifecycle.test.ts` “joins concurrent acquisition and releases every subscription exactly once” and “cleans subscriptions acquired after disposal...” check stronger release/late-attachment behavior; preserve these regressions unchanged.
- Delete standalone “notifies onAssistantCompleted for finished assistant messages” (about 25 lines). Add its hook and exact callback payload assertion to existing “reconciles streaming deltas, citations, and completion”, which already emits and inspects the same accepted completion. This is one natural completion scenario, not an unrelated mega-test. Net approximately 20 lines and one independent controller setup removed.
- Delete controller-only “discovers local models...” (about 16 lines) and “discovers account-visible OpenAI models...” (about 13 lines). These simply configure a mocked API return, call a controller forwarding method and check it returns that same object. Controller's production forwarding methods remain because UI owns them; no tested state transition is lost. Retain provider updates, persisted reasoning, grant/exclusion state and delayed provider race tests.

Expected reduction: 55–65 test LOC; three redundant controller setups plus a callback-only setup removed. Do not delete API tests just because they look similar: native payload normalization, returned optimistic messages, identity, privacy and date context are separate boundaries.

### E. Narrow pure helper inputs and remove irrelevant duplicate DTO factories

Files: `chat/ui/chatPanelHelpers.ts/.test.ts`, `chat/proposalVisibility.ts/.test.ts`.

`resolveTargetMessageId` reads only `excerptMessageIds`; `proposalInitialMarkdown` reads only `preview`; `reviewBelongsToConversation` reads only review.proposalId and proposal.id/conversationId. Narrow their accepted types to these projections (Pick or equivalent structural types), retaining null handling and the exact algorithms. Existing full production objects remain assignable. Replace test-only constructors of complete 20-field Conversation/Proposal objects with direct tiny inputs appropriate to each contract.

Retain every helper assertion, including empty/missing/invalid previews, foreign-conversation proposal identity, draft context identity and safe absolute HTTP(S) URLs. No proxy fake, new helper module or runtime abstraction. Expected reduction: 60–75 test fixture LOC and three irrelevant full DTO constructors; more honest production interfaces. Risk is low and typecheck catches any accidental caller requirement.

### F. Remove genuinely repeated Settings/Atlas fixture construction, not scenario coverage

- `settings/store.test.ts` repeats a Missing Note record in three paging tests and creates manually deferred page handlers despite its existing `deferred<T>()`. Introduce one local typed minimal Missing Note factory/default (fresh timeline per call), reuse existing deferred utility, and use per-case timeline overrides. Retain the normal append, obsolete-page success and obsolete-page error as separate named cases. Estimate 25–40 lines removed with less malformed test data.
- `atlas/atlasStore.test.ts` duplicates the complete pending cloud response across “missing cloud labels...” and “renderer label key...” (about 29 fields each). Define one immutable local pending response used by both, derive labelled variant without mutation; retain both assertions and cases. Estimate 20–25 lines removed. No Atlas production rewrites or pure-helper tests removed: zoom/edge confidence, polling and lifetime admission each own different behavior.

Do not shorten typed AppStore bootstrap/semantic fixtures using `as` casts or null diagnostics: the payload requires those fields and their current typed completeness prevents mistakes already discovered. No full fake generator/proxy is proposed.

## Implementation result

Coordinator approved A–F before edits. Implemented all six items. Settings now owns its six direct IPC calls; history commands still pass through `invokeHistoryCommand`, missing-page limit remains 30, and destructive confirmation remains in the retained history loader. `SettingsViewPayload` moved into the existing store; both consumers use type-only imports. No other module depends on the removed loaders.

The test suite uses one command response map and one IPC spy, replacing four slice spies, two module mocks, and three inconsistent reset blocks. Pending responses are captured at command invocation. Mutation results cannot accidentally become subsequent list/view responses. The serialized-write regression still checks **exactly one** write before its acknowledgement, then exactly two and the merged settings payload. The stale-page fixture now uses the real complete `HistoryModePage` type rather than `unknown`.

No AppStore/listener, privacy, Chat API adapter, late receipt, Atlas invalidation, or Settings state/race test was removed. Chat completion callback coverage was folded into its existing successful stream/completion scenario. Three pure helpers accept only fields they actually read; their algorithms and every existing assertion remain. The new local Missing Note factory and shared pending-cloud value are included in the totals below. No shared helper module was added. The typed fail-fast chat harness remains unchanged.
