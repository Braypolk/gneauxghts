## Released-capture recovery contention

Source: `src-tauri/src/services/note_timeline/editing_window_capture/tests.rs:486–531`; fixture at the beginning of that file. Each of ten iterations creates a new `Fixture`, whose initial note is canonical A; injects a finalization failure for B; starts two `ensure_history_recovered` callers and one canonical C save behind a four-party start barrier; joins them; checks no prepared intent remains, pending hash equals canonical bytes, and final retained history is precisely creation A plus editor C.

There are no explicit sleeps or polling deadlines in this test. Its barrier and joins block, and ten complete fixture/publication lifecycles repeat. The nearby live-publication test's 20 ms negative receive timeout does **not** belong to this test.

Production `runtime.rs:369–407` takes the same `history_recovered` mutex for readers and prepared writers, then protects the released-capture flag and runs `recover_released_publications` once when needed. `history_store.rs:4492` restricts recovery to released receipts, verifies their notes, and replays prepared intents. The simultaneous-start barrier increases the chance of contention but does not prove either reader reaches the recovery mutex while another caller owns it. Ten runs can all serialize without exercising the disputed overlap.

The meaningful replacement is a small deterministic schedule: pause a recovery owner after acquiring the recovery mutex and before replay, establish that another reader and the writer have reached that admission boundary, release, and retain all existing final-state assertions. Reader-first and writer-first ownership are the two useful schedules; the readers are otherwise symmetric. This would require a narrow test-only admission/ownership hook because the existing publication gate controls a live publication rather than released recovery. The hook must have bounded observation waits and unconditional release on failure. Do not add a generic scheduler framework or insert sleeps. Until such a schedule exists and is reviewed, retain the current ten repetitions; reducing their count alone gives up probabilistic coverage without replacing it. Prebuilding A would not remove the defining live B failure/C publication and would introduce unnecessary fixture machinery here.

## Pending keyword search during bulk indexing

Source: `src-tauri/src/commands/search_commands.rs:1522–1618`. The test first waits for queue idle, holds `state.foreground_guard()`, writes 64 notes, and prewarms the real in-memory catalog. It manually indexes Imported 0 while Imported 63 remains pending. Body and title searches for 63 must return keyword hits, identity, and highlights without creating its lexical signature. Searching indexed 0 must return exactly one hit. After releasing foreground activity, the test waits until **all 64** signatures exist, invalidates the result cache, and repeats the target query to prove no duplicate after indexing.

The final wait polls up to 30 s with 25 ms sleeps and scans signatures until all are present. The queue itself also backs off 25 ms while foreground activity is held (`services/background_index_queue.rs:44,246`). The test does not intentionally sleep for 2.80 s; it requires actual projection work. The reported time cannot be divided into indexing versus setup from source alone.

`index.rs:694–731` prewarms every collected entry and enqueues each projection without a batch-size threshold. `lexical.rs:252–299` holds one lexical snapshot, searches catalog notes whose signatures are absent/stale, then includes indexed candidates only when their signatures match. There is no 64-note boundary in either path. A unique target query does not test result truncation; the command's requested limit 12 does not make 64 meaningful. The distinct behavioral roles are one indexed note and one pending note. Two notes preserve all current search/deduplication oracles and the true foreground-paused background handoff. A larger small import is defensible as an import-backlog scenario, but should not be represented as unique threshold coverage.

Recommended bounded change: use two explicit notes (indexed and pending), retaining the real prewarm, foreground guard, signature absence after both searches, ID/highlight/reason assertions, indexed no-duplicate assertion, complete drain, cache invalidation, and post-drain result assertions. This removes 62 actual file writes and queued projections, not merely test-case syntax. It does reduce scale exercise; if bulk throughput is the intended contract, that belongs in a measured scale/performance fixture rather than an unasserted count in this functional test. No speedup amount is claimed.

The existing `wait_until_idle_for_test` uses a condition variable and a five-second deadline (`background_index_queue.rs:99`). It can replace signature polling **only with explicit successful-signature assertions afterward**: idle means all jobs were attempted, not that every projection succeeded. Its five-second bound also differs from this test's 30-second allowance; preserve the intended bound explicitly if needed instead of silently tightening it. Using this helper removes polling noise, but cannot avoid projection cost. Do not seed a fully indexed archive or drop the post-release query; those bypass the pending-to-indexed contract.

## Missing-note paging, restart, and recovery

Source: `src-tauri/src/commands/history_commands.rs:1350–1541`. Setup publishes Version 0 and then 35 individually finalized versions. It names the oldest revision, corrupts that oldest revision's source discriminator, deletes the canonical file, and records a Missing observation. The first real command must return exactly 30 records, Missing first, and a cursor despite the damaged out-of-page record. It repairs that source before restarting the app. The saved cursor must then return exactly eight nonoverlapping older records, no further cursor, and the oldest name; an instrumentation counter must remain zero to rule out exhaustive integrity sweeps. Wrong-note and post-reset cursors must be Stale, and actual recovery must recreate a canonical file after reset.

There are no explicit sleeps or polling loops. The seed loop is repeated real writer/finalization work, not part of the command's paging algorithm. The 38-record geometry is directly asserted (36 revisions plus the retained lifecycle records); reducing versions would change the exact 30+8 contract. Although fewer records beyond the first page could still exercise continuation, this is a weaker opportunity than replacing the seed while preserving the exact oracle. The oldest corrupt record must remain outside page one, and older-page naming plus restart and generation validation must stay live.

Potential future fixture: a clean, closed, canonical-generated 36-revision history, loaded into an isolated vault using the existing test-fixture portability discipline. Keep naming, corruption, external deletion, Missing observation, first page, source repair, restart, second page, stale cursors, reset, and recovery in the test. Do not load an already-missing or already-corrupt fixture, and do not replace the two production app lifetimes with a fake page provider. Existing prebuilt geometries do not match this exact contract; adding another archive/recipe/manifest requires demonstrated net benefit. At 1.82 s reported for the whole test, retain the current implementation unless setup measurements justify that maintenance cost. Do not reuse a poisoned or reset AppState across cases.

## Corruption detected after prior attestation

Source: `src-tauri/src/commands/history_commands.rs:962–1047,1150–1229`. `ErrorFixture::new` creates isolated app data and notes, a real mock-Tauri-managed AppState, real Before and After publications, finalizes the editor window, performs a successful production history page read, and captures the newest revision ID. Each of nine damage variants gets its own such fixture.

The variants are Payload, WindowEvidence, ReciprocalEvidence, PayloadVersion, DatabaseBytes, DeltaLength, Lineage, Predecessor, and Ancestry. They deliberately enter different consumers: parent diff for ancestry, page records for evidence/lineage/predecessor, revision reconstruction for payload/database/version/length. Every branch then requires the exact typed Corrupt response, unchanged scan counters, Corrupt on a later header-only page read, rejected canonical publication, unchanged canonical bytes, and unchanged scan counters again.

There are no test sleeps, polling loops, or repeated equivalent schedules here. Equal external error classes do not make the corrupt structures redundant: deleting variants would lose validation paths. A fresh owner is required because corruption latches in runtime state. Resetting the flag between variants would bypass the property being verified. The successful read before mutation is essential; a pre-corrupted archive tests startup rejection instead of corruption discovered after attestation.

The clean two-revision seed could theoretically be cloned before each fresh attestation, but it is already small, and fixture archive/restore/attestation overhead has not been measured against two publications. No such optimization is recommended on the available evidence. Retain all nine variants and exact no-write/no-rescan checks. If root measurements identify fixture construction as dominant, measure a clean seed clone independently before adopting it; do not disable integrity verification or background work merely to improve this timing.

## Priority and evidence limits

1. Pending-search fixture geometry is the strongest straightforward opportunity: remove unnecessary per-note I/O while retaining real queue ownership and all result oracles.
2. Recovery repetitions offer a stronger correctness improvement if replaced by explicit contention schedules, but need a carefully bounded test hook; this is not a count-only trim.
3. Missing-note seed replacement is possible but conditional on a measured setup cost large enough to justify another portable fixture.
4. Keep the corruption matrix intact.

These conclusions classify work and coverage from source. They do not establish speedups, stability distributions, or fixture load costs. Root owns those experiments and any subsequent implementation authorization.
