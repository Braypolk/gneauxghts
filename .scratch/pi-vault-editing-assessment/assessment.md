# Pi vault editing assessment

Historical assessment. The recommendation was implemented and tested in the
[Pi note editing slice](../archive/pi-note-editing.md); current architecture and
acceptance are recorded there and in the authoritative architecture documents.

Research date: 2026-10-17. Scope: installed `@earendil-works/pi-durable` **1.3.0**, compared with the pinned official upstream revision `4954d760504c11df9b2cbdc040346107b6a8153d`. This is an architectural assessment, not an implementation plan or a passing acceptance result. Existing unrelated working-tree changes were not modified.

## Assessment

**Recommendation:** retain the native canonical-mutation boundary, but reevaluate the publication orchestration while building a real Pi edit tool. Pi should own tool execution, task lifetime, durable continuation and review state. Native code should own vault authority, exact content/base checks, canonical mutation and receipts. Reusing an existing custom one-phase task merely because it passes synthetic tests would be premature.

The strongest reuse candidate is **a Pi tool wrapper that runs the stock edit implementation against an in-memory staging environment**, then publishes the exact candidate through the native note boundary. This uses the public Pi API without copying its matching engine. It needs a small prototype before commitment: the wide environment interface and the application's Note Identity/read-receipt contract may make a domain tool with a newly public upstream pure-edit helper cleaner.

## Observed Pi facts

- `createEditTool()` is exported by `@earendil-works/pi-durable/tools`. It accepts `path` plus `edits[{oldText,newText}]`, repairs several model argument shapes, reads the target, computes a replacement, calls `env.writeFile`, and returns model text plus UI diff/patch details. It does not require installation of the broader `CodingTools` bundle. [Installed factory](../../node_modules/@earendil-works/pi-durable/dist/tools/edit.js), [public tools exports](../../node_modules/@earendil-works/pi-durable/dist/tools/index.js).
- The matching engine tries exact text, then normalizes trailing whitespace, smart quotes, Unicode dashes and special spaces. It rejects empty, ambiguous, overlapping and no-op replacements; all replacements address the original file. It preserves BOM and original newline style; fuzzy edits preserve untouched line blocks, although touched lines can adopt normalization. This is materially more behavior than a simple `String.replace`. [Installed matching source](../../node_modules/@earendil-works/pi-durable/dist/tools/edit-diff.js), [factory](../../node_modules/@earendil-works/pi-durable/dist/tools/edit.js).
- The pure matching/diff functions exist internally, but are **not public package subpath exports** and are not re-exported from `/tools`. Deep-importing `/dist/tools/edit-diff.js` would depend on package internals and conflicts with its exports map. [Package exports](../../node_modules/@earendil-works/pi-durable/package.json), [tool exports](../../node_modules/@earendil-works/pi-durable/dist/tools/index.js).
- `ExecutionEnv` is a broad filesystem-and-shell interface. Stock edit uses path resolution, canonical path, file metadata, text read and file write; unused operations can deny capability in a narrow adapter. `HarnessOptions.env` receives conversation ID, cwd and a document reader, **not the current call/task ID**. A wrapper does receive that identity and can replace `api.env`; the public API explicitly says it is a plain object suitable for spreading. [Environment types](../../node_modules/@earendil-works/pi-durable/dist/env/index.d.ts), [tool API and environment factory types](../../node_modules/@earendil-works/pi-durable/dist/harness/types.d.ts), [pinned official types](https://raw.githubusercontent.com/earendil-works/pi/4954d760504c11df9b2cbdc040346107b6a8153d/packages/durable/src/harness/types.ts).
- `wrapTool` decorates whichever enabled same-name tool won registry resolution. `beforeTool` can block or change arguments before intent; `afterTool` replaces the execution result. These are useful policy and presentation seams, but an after-hook cannot make an already-performed file write reviewable beforehand. [Installed hooks/types](../../node_modules/@earendil-works/pi-durable/dist/harness/types.d.ts), [wrapper implementation](../../node_modules/@earendil-works/pi-durable/dist/harness/define.js).

## Durability boundaries that matter

**Observed:** Pi commits tool intent before execution, owns tool tasks, supports task-owned documents and durable memos, and supplies task cancellation/ownership/continuation. `memo` stores a candidate unless a winner already exists. Nested tool calls use durable keys to reacquire earlier calls. These features should replace custom transcript-backed run state or a second JS scheduler if either is introduced. [Installed runtime types](../../node_modules/@earendil-works/pi-durable/dist/types.d.ts), [tool implementation](../../node_modules/@earendil-works/pi-durable/dist/harness/tool.js), [pinned official documentation](https://github.com/earendil-works/pi/blob/4954d760504c11df9b2cbdc040346107b6a8153d/packages/durable/README.md#tools).

**Observed:** stock `edit` has no `replay: 'safe'`; default interrupted execution yields an error saying it may have partially run. It checks cancellation **after** `writeFile` succeeds, so an effect can exist even when its returned result is an abort/error. Pi does not make a separate native write and a Pi transcript commit one transaction. Declaring a wrapper replay-safe requires external-effect idempotency/reconciliation, not merely a memo or nested-tool key. [Edit source](../../node_modules/@earendil-works/pi-durable/dist/tools/edit.js), [tool replay implementation](../../node_modules/@earendil-works/pi-durable/dist/harness/tool.js).

**Observed:** Pi's mutation queue is a process-local `Map` keyed by environment ID and canonical path. It serializes Pi edit/write calls, explicitly excluding other processes and bash. It is not a replacement for editor exclusion, native conflict checks or canonical publication ownership. [Queue source](../../node_modules/@earendil-works/pi-durable/dist/tools/file-mutation-queue.js).

**Observed:** persisted task `waiting` waits on task IDs. Documents can be watched and tasks can await watches in a restartable phase, but 1.3.0 does not provide a generic persisted `waiting-on-document` state or a complete human review workflow. Approval needs application-defined state/UI and wake/continuation behavior on top of Pi primitives. A non-replay-safe tool's owned child tasks default to abandonment on restart. [Task states/runtime](../../node_modules/@earendil-works/pi-durable/dist/types.d.ts), [child task creation](../../node_modules/@earendil-works/pi-durable/dist/harness/tool.js).

**Inference:** stock edit's own fresh read is weaker than binding the edit to the model's earlier read. It can accept an unchanged target block after unrelated context changes. The adapter should stage the exact model-read snapshot and retain its native read receipt, or expose an explicit expected source ID. Obtaining a fresh receipt invisibly inside edit would defeat that intended stale-base guarantee. Current `read_note` already issues native source IDs, while the native-facing update shape requires `expectedReadSourceId`. [Current read tool](../../src/lib/features/chat/pi/notes.ts), [current mutation shape](../../src/lib/features/chat/pi/publication.ts).

The receipt supplies metadata/hash/path, not an immutable copy of the original Markdown. The adapter must locate or capture that content and validate it against the expected source hash before staging. Candidate snapshot ownership remains a design question. A full-Markdown native commit payload does not require a full-Markdown model-facing tool: targeted Pi edits can produce that exact commit payload.

## Alternatives

| Approach | Benefit | Cost / architectural concern | Recommendation |
|---|---|---|---|
| Stock edit with native-backed environment | Maximum stock execution reuse | `writeFile` must hide approval, per-call intent identity, receipts and recovery behind a filesystem-shaped `void` result. Global env factory lacks call ID. Holds Pi's per-file queue while approval waits. Still needs a wrapper for trustworthy outcome/replay. | Possible, but prototype only if it produces a simpler interface than staging. |
| Wrapper + stock edit + staging environment + native publication | Public Pi matching, repair, validation and diff behavior; canonical effects remain explicit; staging aborts cannot mutate vault | Needs a bounded environment adapter and exact snapshot capture. Must persist prepared intent/reference before continuation; do not return stock success until canonical publication is confirmed. | Best initial candidate to test. |
| Domain `edit_note` using Pi pure-edit helper | Model receives Note Identity/source ID rather than accidental filesystem semantics; clean domain interface | Helper is private today. Copying matching logic creates an upstream maintenance burden; deep imports are brittle. | Prefer if upstream exports a pure helper, or if a measured adapter cost justifies a clearly maintained fork. |

## Candidates for redesign, not automatic preservation

- The current `PublicationTask` has a single `publish` phase. Decide whether a real replay-safe tool should invoke native publication directly using a memoized intent, or compose a review/publication child task. Keep the extra task only if its lifecycle earns that boundary. Pi already supplies `pi.tool`; another task does not create additional atomicity with native storage. [Current task](../../src/lib/features/chat/pi/publication.ts), [Pi tool task](../../node_modules/@earendil-works/pi-durable/dist/harness/tool.js).
- Keep the authority/read-base/receipt checks whose owner is native state. Reevaluate redundant caches, JS globals or duplicate UI status once a genuine tool drives them; upstream task/doc state may replace orchestration responsibilities but cannot establish native mutation truth. Parent investigation will supply the concrete ownership findings.
- Do not broaden to arbitrary vault files merely because Pi accepts paths. Notes, attachments, renames and deletes have different domain consequences. Exposing the stock schema through an adapter is a product/API choice, not a prerequisite for Pi alignment.

## Verification limits and next evidence

The installed 1.3.0 package is the executable source of truth for these findings. The official pinned README and harness types were verified through the web. Web retrieval of the pinned edit source paths failed (cache miss), so their behavior is established by the installed package, not claimed to be independently byte-verified against that revision. Upstream README labels the API experimental. No assertion about a newer release is made.

The parent added a reproducible [direct stock API probe](edit-adapter-probe.mjs): `node .scratch/pi-vault-editing-assessment/edit-adapter-probe.mjs`. I reran it successfully. Six cases establish targeted replacement/diff output, ambiguous-match denial without write, loss of a synthetic concurrent edit between read/write, cancellation throwing after changed bytes, failed repeat of an already-applied replacement, and staging that preserves BOM/CRLF without changing canonical content. This is **synthetic direct execution**, bypassing Harness schema preparation, task restart and native/editor/mobile integration; it does not establish adapter acceptance.

Before selecting the adapter, exercise real Pi task execution with unchanged target after changed surrounding context, rejected review, restart while waiting, cancellation after native commit and crash before Pi result commit. Compare the number of application-owned states and recovery branches, not only code size. Native receipts must make the last two return the committed truth.

## Local native/editor ownership findings

### Provenance and the actual retained boundary

Both `pi/publication.ts` and `pi_chat/publication.rs` were added in the Pi rebuild commit `dd5292a7`; they are not the old runtime preserved behind renamed files. The old `chat/note_proposals.rs` persisted mutable proposal drafts, hunk decisions, proposal/run/message links and promotion associations. That module is gone. The document boundary's former `adoptAcceptedProposal` was replaced by a short `withAgentPublication` operation. Inspect with `git show dd5292a7^:src-tauri/src/chat/note_proposals.rs` and `git show dd5292a7 -- src/lib/features/notepad/document/documentEditingService.ts`. New provenance does not itself justify retention: compare responsibilities and callers below.

| Responsibility | Actual current owner | Assessment |
|---|---|---|
| Model/tool invocation, validation, durable intent, generic progress and restart scheduling | Pi `ToolTask` and Harness | Build on Pi. Do not introduce another controller or native run queue. |
| Matching targeted replacements, argument repair, line-ending handling and diff generation | Upstream edit tool; not implemented by the current publication foundation | Reuse the public factory if staging remains a small adapter. Avoid a second matching/diff engine. |
| Editable review draft, working version, waiting and continuation | Not shipped in current chat | Design on Pi documents/tasks. Do not restore native mutable proposal/hunk tables or the former global review workflow merely for parity. |
| Current grants, revocation, accepted payload/base and execution proof | Native authority and immutable mutation intents | Retain this authority boundary. Native accepted/rejected authorization records have a different job from a Pi review document's working state; a UI document alone cannot authorize an effect. |
| Canonical file, Note Identity, history capture, indexes/tasks and committed warnings | NoteTimeline | Retain the canonical mutation owner. A raw file write plus watcher replay would change the guarantees and Mutation Source. |
| Unsaved document protection, short edit exclusion, committed adoption and WebView lifetime | DocumentEditingService plus native editor admissions | Retain the behaviors; simplify the binding mechanism only with replacement evidence. Pi's file queue cannot observe dirty Svelte documents or join native effects on page replacement. |

Sources: [registry composition](../../src/lib/features/chat/pi/runtime.ts), [native authorization/intents](../../src-tauri/src/pi_chat/publication.rs), [native grants](../../src-tauri/src/pi_chat/authority.rs), [canonical publication/proof](../../src-tauri/src/services/note_timeline/publication.rs), [document lease/adoption](../../src/lib/features/notepad/document/documentEditingService.ts), [workspace mount/teardown](../../src/lib/features/notepad/Notepad.svelte).

The native mutation table contains the exact request, scoped authority revision, accepted/rejected payload, publication proof and result. It does not schedule model turns, persist editable hunks or own a pending-review queue. Its result is external-effect evidence, not a second Pi conversation/task projection. If that table acquires review progression, model retry or mutable draft ownership during the next feature, that would cross the accepted Pi boundary.

### Concrete candidates to reopen

1. **The current task-only interface is a foundation, not the future product design.** Mutation preparation, approval and synthetic task creation currently come from tests/acceptance harnesses; no production model tool drives them. Integrate a real tool before freezing the wrapper/task split. A native full-Markdown request can stay an implementation detail beneath Pi's targeted edit schema.
2. **The extra publication task must earn its boundary, but it is not automatically redundant.** It is a registered Pi task, not a second scheduler. Its `abort` handler reconciles native truth and can retain a committed outcome after Stop; upstream `ToolTask.abort` settles an aborted tool result. This is a concrete reason to test a publication child task against a direct tool implementation. Do not delete it merely because `pi.tool` exists, or retain it merely because acceptance fixtures create it. The complete UI/model outcome after cancellation still needs integration proof. [Current task](../../src/lib/features/chat/pi/publication.ts), [upstream tool abort](../../node_modules/@earendil-works/pi-durable/dist/harness/tool.js).
3. **The module-global publication owner is lifecycle plumbing, not evidence Pi should own editor state.** It coordinates route withdrawal, native effect settlement and retained editor roots. Its complexity merits review in the actual tool composition, but moving it into a Pi document would create a stale mirror of live editor ownership. There is no demonstrated drop-in upstream replacement.
4. **Off/Temporary/Always and review default-on are accepted product choices, not Pi requirements.** Reevaluate their user interaction explicitly if a simpler workflow is desired. Existing tests do not decide that UX. The existing ADR permits future review working state in Pi while native code retains accepted authorization. [ADR 0012](../../docs/adr/0012-found-ordinary-chat-on-pi.md).
5. **Historical compatibility is narrow.** The remaining `acceptedChatProposal` deserialization alias reads retained Note Timeline records as `AgentPublication`; it does not preserve the old proposal engine or expose old write APIs. Removing historical decoding would be a data-format decision, not necessary to adopt Pi tools. [Mutation Source](../../src-tauri/src/services/note_timeline/domain.rs).

### Recommended next decision and acceptance

Build one disposable, real-Harness read/edit/review/publish/reopen slice using the public stock edit factory and a staging wrapper. Compare direct tool publication with a Pi-owned review/publication child task only where their behavior differs. Select the version with fewer application-owned execution states and a clear committed-effect outcome. Replace superseded orchestration and its structural tests in the same implementation; keep behavioral acceptance for permission, conflict, canonical history and recovery.

The slice must establish: exact expected read snapshot rather than a silently refreshed base; review rejection with zero canonical writes; edited review content requiring a new exact acceptance; restart during review without losing the draft; authority revocation and dirty-editor denial; crash after native commit without duplicate publication; and truthful effect presentation when Stop arrives after commit. Include changed surrounding content even when `oldText` still matches. Keep the editor lease around publication only, never around the human review wait. Broader file types and rename/delete need concrete domain contracts before widening the capability.

This would extend the accepted ownership direction in ADR 0012, not restore its superseded proposal-only runtime. Any later change to scope/grant policy or the native canonical owner should amend that decision explicitly.
