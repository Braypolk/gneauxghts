# Product scale cost audit — 2026-10-16

Read-only source audit of frozen product `b52b1a6`; no measured attribution or performance improvement is claimed. Scale v5 is still running, so this does not establish its eventual acceptance result. The 1005-conversation/1005-input fixture and its budgets remain unchanged.

The scale seed waits for correlated terminal events (`productScaleProbe.ts:69–80`). Its five-second driver progress poll reads only in-memory fields (`product-scale-gate.mjs:259–265`); it does not poll `getConversation`. This differs from the earlier shared-resource fixture's full-conversation polling. The normal mounted controller adopts the supplied completion event rather than reloading conversation/list on every terminal event (`controller.svelte.ts:183–208`, `controllerMachine.ts:507–514`).

The actual adapter completion path waits for `getConversation` before emitting the terminal event (`chatApi.ts:365–383`). That reconstruction visits every historical submission and per-origin/admitted-answer documents, validates sources, computes usage/activity, and finally rescans submissions/entries through `summary`. For N completed source-free turns, the two source-validation paths can issue roughly 2N sequential native validations even when their source arrays are empty (`chatApi.ts:178,303,308`). Native validation still prepares policy scope. Missing `SummaryUsageRun` snapshots also repeat SQL lookups: upstream caches existing documents, but its missing-document branch does not retain a negative cache (`@earendil-works/pi-durable/dist/session/session.js:625–637`). Snapshot calls must not all be counted as SQL because existing documents can hit cache.

Each durable request entry retains the projected history frozen for that request (`chatApi.ts:345,353,358`). `entriesFor` retrieves complete record JSON. Before compaction, constant-size messages can therefore yield quadratic retained/request-history read bytes, without recursively nesting histories. Admission, reconstruction, summary and independent transcript publication repeat scans. Per-submission array searches/filtering also amplify CPU cost. These are source-backed mechanisms; the audit cannot rank their actual contributions. Transcript publication shares the serialized native SQL facade and can contend with terminal projection.

Potential bounded optimizations include skipping validation only when both issued sources and read events are empty, status-filtered limit-one unfinished-submission checks, local maps/adjacent boundaries for one reconstruction, and reusing that call's loaded entries/submissions for its summary. None was implemented by this audit. They must preserve policy epochs, live-settlement reconciliation, exact history/activity/usage and transcript behavior. No new persistent projection cache or coordination owner is proposed.

A useful subsequent measurement separates admission→receipt, receipt→durable settlement, settlement→terminal delivery, transcript queue time, empty/nonempty native source validations, missing summary lookups and entry-scan response bytes. The existing scale invoke hook is unavailable on its immutable native boundary, so null counters remain unknown. No bridge totals are inferred from source inspection.

No correctness failure was demonstrated. Reconstruction failure after durable settlement can reach the broad request failure handler (`chatApi.ts:386`), which deserves a separate focused reproduction before changing terminal semantics. Existing settlement reconciliation must remain intact.
