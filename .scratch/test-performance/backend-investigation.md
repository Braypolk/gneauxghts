# Rust fixture performance investigation

Status: ready-for-agent
Progress: Read-only investigation complete; timing and any experimental instrumentation remain coordinator-owned.
Owner: audit_timeline

## Main assessment

Separate **test-environment lock wait**, **fixture construction**, **scenario work**, **projection join**, **final resource destruction**, and **directory removal** before choosing an optimization. Current code supports several plausible costs, but none has been timed in this investigation. Do not interpret long parallel per-test durations as intrinsic fixture cost.

The investigation follows the diagnosing-bugs skill and this phase's spec. No Cargo command, build, test, benchmark, source edit or dependency change was made. The source observations below are hypotheses for coordinator experiments, not measured causes.

## Actual ownership and lifetime

1. `test_support.rs:14–22`: `lock_test_env` acquires a single process-wide mutex, then captures mutable path configuration. A test waiting here has not created its vault or started its body. The guard also serializes process-wide fault hooks; it is more than a temporary-directory naming guard.
2. `test_support.rs:48–64`: `TestVault::new` keeps that guard for its entire lifetime, creates two canonicalized temp directories, changes global app-data/notes inputs, creates disabled semantic state, and constructs real `AppState`. Static search found 319 matching `TestVault::new`/`lock_test_env` lines across 42 files; this is source inventory, **not** 319 independently counted tests.
3. `index.rs:175–197`: every AppState creates timeline runtime/store context, binds SQLite app-state storage, constructs real lexical index, and starts `BackgroundIndexQueue`. Semantic-disabled is not lexical-disabled. `SemanticState::new_disabled` (`semantic/mod.rs:406`) itself creates settings/debug state, without starting the active embedding/indexer machinery.
4. `test_support.rs:68–72`: fixture drop first calls `shutdown_discard_and_join`. It discards queued rebuildable work but waits for any projection already executing. With the fixture's Arc as the last AppState owner, subsequent field destruction drops state, then notes/data directories, then the environment guard. All of that occurs before the next guarded fixture enters. Escaped state Arcs would alter the final destruction timing; identify them before attributing destructor samples.
5. `BackgroundIndexQueue::Drop` calls the same shutdown again, but the JoinHandle was already taken, making the normal second call cheap. Removing the explicit fixture stop would change ordering: worker-owned resources could remain active while other AppState fields/directories are destroyed. Do not remove it as redundant overhead.
6. `TestEnvGuard::drop` restores paths and clears global fault hooks before releasing its lock. `TestDir::drop` recursively removes files. These are separate teardown categories from the projection worker join.

## Other limits relevant to isolation

- `state/persistence.rs:828–875` uses a test-thread-local storage binding when available, but worker threads do not inherit it. They can fall back to the global running-state binding and mutable path selection in tests. AppState construction also publishes a global compatibility binding. Thread-local optimization is **not** evidence that fixture environment locks can be removed.
- Timeline open coordination has a global `HISTORY_STORE_OPEN_LOCK`; canonical file mutation and history observations have separate global locks. A full serial test run removes competition between tests but leaves actual scenario thread contention intact.
- Timeline runtime drop signals window scheduler and verification cancellation (`runtime.rs:494`; `runtime/windows.rs:178`; `runtime/verification.rs:329`). These are not projection JoinHandles. A scheduler may briefly outlive AppState while holding only bound runtime coordination. Do not misclassify this as a synchronous one-second destructor delay; use lifetime probes if measurement suggests lingering work. No new lifecycle defect is asserted by this inspection.
- History uses `synchronous=FULL` and durable publication intentionally. Existing corruption, restart, rollback and no-overwrite cases must continue to hit real persistence. Disabling sync, in-memory replacement databases, shared mutable fixtures, or skipping projection work would be behavioral changes, not safe default performance fixes.
- The installed Tantivy filesystem watcher has a500ms poll constant, but this code uses `Index::create_in_ram`. No evidence connects that filesystem watcher to these fixtures; it is not a proposed explanation for a500ms test floor.

## Suggested next measurement order

1. Coordinator's serial versus parallel identical-binary baseline, excluding compilation.
2. If attribution is still uncertain, temporary compact fixture spans: wait for environment, construct paths/AppState, scenario, projection join, final state destruction, directory cleanup. Keep exact test IDs and record aggregate exclusive durations; do not sum parallel overlapping wall spans.
3. Take one cheap TestVault case and the two existing inventory workloads. Determine whether constructor, repeated publication or query assertions dominate.
4. Only then run the single-worker real lexical-index experiment if supported by spans. Preserve/restore the source checkpoint and retain negative results. No broader fixture or production rewrite proposed without those measurements.

No implementation is recommended solely from this static investigation. The best initial targets are identifying lock wait and separating real lexical/durable seed work from teardown attribution.
