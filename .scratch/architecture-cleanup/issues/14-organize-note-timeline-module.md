## Target organization

Keep the existing `services::note_timeline` import surface and one canonical NoteTimeline owner. The parent file should provide module declarations, intentional re-exports, the owner/binding definition and a short responsibility map. Cohesive implementation blocks can live in private child modules on the same existing types; do not invent objects to route calls between files.

Use these responsibility groups as the initial extraction map, adjusting file names or combining closely coupled groups where that keeps privacy simple:

| Private group | Existing implementation to place there |
|---|---|
| Domain records/results | Identity and record vocabulary, mutation results/warnings, receipts and serialization; keep capability construction restricted to the timeline module. Avoid one-file-per-type fragmentation. |
| History Mode | Page/context queries, reconstruction-facing DTOs, diff/asset helpers, role-limited HistoryModeAccess and restore. Keep complete restore orchestration together. |
| Current content | CurrentContentAccess, eligibility/projection checks and delivery validation. |
| Publication | Existing preparation/save/mutate implementations and their private helpers. Keep each operation's lock/preparation/write/finalization sequence contiguous. |
| Observation/lifecycle | Retained observation replay, external transitions and missing/lifecycle handling; these may be two files where their helpers are cohesive. Reuse existing forgotten module rather than duplicate it. |
| Administration | Existing baseline initialization, history health/reset/clear/compaction and close implementation; keep each complete operation together. |
| Tests/support | Move the inline suite into behavior-grouped test files under the module and consolidate its existing shared fixtures privately. Preserve test and E2E gating. |

No target line limit is imposed. The result must expose understandable responsibilities, not just cut the file into numbered chunks or relocate the entire monolith into one new file.
