# Remaining Pi reuse audit

Historical pre-alignment audit plus implementation amendment. See [the accepted outcome](outcome.md) for final verified behavior; this is not an executable backlog.


Research only, 2026-10-16. Inspected installed `@earendil-works/pi-durable`, `pi-ai`, and `chord`, all reporting **1.3.0** (`package.json:49–51`, each installed package's `package.json:3`). Official version-tagged documentation was also checked: [Durable](https://github.com/earendil-works/pi/blob/v1.3.0/packages/durable/README.md), [AI](https://github.com/earendil-works/pi/blob/v1.3.0/packages/ai/README.md), and [Chord](https://github.com/earendil-works/pi/blob/v1.3.0/packages/chord/README.md). Recommendations below use the installed declarations/implementation; they require no claim about a newer release. No application, vault, database, or implementation was changed.

## Assessment

There are modest simplifications available, especially in disposable UI observation and catalog plumbing. The inspected code does **not** retain a competing ordinary-chat execution engine: it composes upstream `SqliteStorage`/`Harness`, submits input through Pi, and calls Pi abort/configuration APIs. Most remaining native code implements application authority, credential isolation, Tauri transport, and SQLite lifetime guarantees that upstream cannot supply. This agrees with [ADR 0012](../../../docs/adr/0012-found-ordinary-chat-on-pi.md) and the [architecture's Agent runtime section](../../../ARCHITECTURE.md).

## Boundaries worth keeping

**Provider parsing is already upstream; admission cannot become a generation hook.** `nativeProvider.ts:124–152` uses Pi's completions/responses parsers and forwards their normalized stream while intercepting terminal success for native citation/authority admission. AI's public `fetch`, `onPayload`, `onResponse`, and `onProviderStreamEvent` exist (`dist/types.d.ts:47–72,101–112`), but `onResponse` receives status/headers (`:42–45`), and stream-event observation is read-only and precedes normalization. None is a drop-in normalized terminal-message replacement. Durable `HookRunner.each` reports ordinary thrown errors and proceeds (`dist/types.d.ts:120–126`); built-in compaction calls `models.completeSimple` directly with the same provider session (`dist/harness/compaction.js:119–128`). Therefore retain admission in the shared provider wrapper/native seam. The native fetch is already using upstream's intended custom-fetch extension; replacing it with ordinary WebView HTTP would abandon native endpoint/credential control (`transport.rs:57–83,147–168`).

**The native SQLite protocol is an adapter, not a second chat scheduler.** Upstream's `SqliteDatabase` explicitly requires operation queuing around async transaction callbacks, expiring transaction handles, settlement only after commit/rollback, and a distinguishable rollback failure (`dist/storage/sqlite/database.d.ts:16–35`; [official contract](https://github.com/earendil-works/pi/blob/v1.3.0/packages/durable/src/storage/sqlite/database.ts)). `nativeSqlite.ts:20–67` implements exactly those requirements. The bundled Node adapter implements comparable queue/scope/rollback logic but imports `node:sqlite` and `node:fs` (`dist/storage/sqlite/node.js:1–3,105–150`); the Cloudflare adapter requires Durable Object storage (`dist/storage/sqlite/cloudflare.js:95–140`). Neither replaces a Rust/Tauri adapter. Rust additionally owns revoked WebView generations, abandoned transaction leases, native SQL confinement and checkpoint/close (`storage.rs:85–107,227–337`). Removing the JS queue because Rust also gates SQL can admit unrelated facade operations into the gaps between `begin`, callback operations and `commit`; retain the interface guarantee. IPC batching/caching would be a separately measured adapter optimization.

**The human transcript is intentionally wider than Pi's active view.** Installed `ConversationView` contains only active entries and built-in documents (`dist/harness/view.d.ts:5–11`; mounted kinds in `dist/harness/view.js:13–20`). It omits pre-compaction entries and custom `ChatDoc`. Consequently `conversation.entries()` paging/merging and a separate title-document watch (`piConversationView.ts:108–122,137–162,229–233`) are justified. `viewState()`/`documentState()` can replace watch mechanics if convenient for Svelte, but cannot replace complete history paging. Do not delete historical paging under the assumption `view.entries` is the human transcript.

**Stop/withdraw and Harness close are already delegated correctly.** UI Stop and withdrawal use `conversation.abort({ background: true })` and `harness.abortSubmission` (`piConversationView.ts:188–194,235–238`); Pi owns queued-input withdrawal, background scope and task settlement (`dist/harness/types.d.ts:67–74,623–627,659–665`). `runtime.ts:128–132` awaits `harness.close`; upstream seals admission, joins task invocations and closes storage (`dist/session/session.js:306–336`, `dist/harness/harness.js:215–217`, `dist/harness/scheduler.js:163–171`). Native restart acknowledgement, outstanding HTTP cancellation/join and revoked database owners still bridge separate process/WebView lifetimes (`runtime.ts:155–156`; `transport.rs:38–48`; `storage.rs:111–225`). They should not be replaced with a second Pi wait loop or removed because Harness close exists.

**Boot-time binding restoration is necessary application integration.** `runtime.ts:135–165` installs provider-session/native-authority mappings and model metadata before enabling scheduling. Pi persists provider session identities but cannot reconstruct the application's native authority bindings. Its documented automatic scheduler start on submit/abort/wait (`dist/harness/types.d.ts:642–645`) also means the ordering deserves preservation, including the existing completion of mapping installation before aborting denied conversations.

## Composer drafts: feasible consolidation, conditional payoff

A Pi **session-scoped document family keyed by the existing slot string** could replace the dedicated native draft table and two CRUD commands. Session scope exists independently of any conversation, so both a pane's pre-conversation draft and `pi-conversation:<id>` drafts fit the same family. Typed APIs provide `snapshot(Family, key, context)`, `tx.doc(Family, key, seed)` and `tx.retireDoc(Family, key)` (`durable/dist/types.d.ts:70–96,759–765,836`). Note the precise definition: **session documents omit `history` and `fork`**; `history: 'latest'` is only a conversation-document option (`:30–50`). Session documents are intrinsically current-only in SQLite (`dist/storage/sqlite/storage.js:57`).

The removable native surface is comparatively small: table creation (`chat_domain.rs:234`), slot validation (`:562–570`), roughly 38 lines of CRUD (`:445–481`), two Tauri wrappers (`commands/pi_chat_commands.rs:210–225`) and registration (`lib.rs:416–417`). `ChatPanel.svelte:35` would switch its injected draft read/write functions from `invoke` to Pi snapshot/commit functions. **The 188-line `composerDraftPersistence.ts` does not disappear.** Its 400 ms debounce, pending draft cache, per-slot remount ordering, stale-load/typing protection, flush, and promotion behavior remain UI responsibilities (`:3,14–21,53–81,89–123,131–176`). Pi serializes admitted commits; it cannot infer the newer user draft before that draft reaches its mutation line.

Storage cost makes this a tradeoff, not an automatic win:

- Existing native writes are one `DELETE` or `UPSERT` (`chat_domain.rs:464–479`). A Pi draft write uses the normal Session mutation line, Chord tracking, and a SQLite transaction with metadata reads, document validation, content writes and sequence update (`dist/session/transaction.js:765–775`; `dist/storage/sqlite/storage.js:107–122,531–557,647–655`). Each SQL operation crosses the current native facade (`nativeSqlite.ts:32–47`), so it is structurally more work per debounced save. Latency/energy impact has not been measured.
- Current-only semantics **do not mean every edit automatically replaces its storage base**: ordinary document edits append deltas; only a base checkpoint prunes earlier revisions (`dist/session/transaction.js:771–775`; `dist/storage/sqlite/storage.js:650–655`). For an unsent `{ body }` draft, use `checkpointWhen: () => true` to keep one current base instead of retaining intermediate draft strings in a replay chain (`dist/types.d.ts:65–66`; `dist/session/transaction.js:593–599`). This changes Pi's own document checkpoint policy, not model transcript history. Logical pruning is not physical secure erasure of SQLite/WAL bytes.
- `retireDoc` removes current-only content but retains the retired document record (`dist/storage/sqlite/storage.js:657–664`); repeated retire/recreate cycles allocate new incarnations. Choose deliberately between a persistent empty-body member and retirement, rather than assuming Pi retirement equals native row deletion.
- A non-exempt storage failure on a draft commit fails the shared Pi Session (`dist/session/session.js:780–797`), coupling draft persistence to ordinary chat availability. Opening/closing drafts also becomes dependent on Harness lifetime. Today's controller reports a save failure independently (`composerDraftPersistence.ts:59–62`). Preserve shutdown/background-flush ordering (`ChatPanel.svelte:67`) and existing persisted unsent text if a migration is ever implemented.

The draft document need not be model input: it is neither an entry nor a prompt section. Generation sends the messages derived from entries (`dist/harness/generation.js:116,315`), and built-in conversation views mount only known built-in documents (`dist/harness/view.js:13–20`). Do not add a section or tool that reads the draft. This is a storage consolidation opportunity, **not duplicate execution ownership**. Given the small native CRUD surface, heavier IPC path and failure coupling, retain the current implementation unless reducing storage surfaces is an explicit priority and measured draft-save cost is acceptable. A future switch must update the architecture's current native-draft ownership statement.

## Low-risk application optimization: startup model registration

`runtime.ts:139–151` restores every historical conversation's native binding and calls `registerModel` for each one, including repeated provider/model pairs. `nativeProvider.ts:169–185` invokes native configuration/discovery each time and resets its post-inference observation marker. Deduplicate successful registrations by `(provider, modelId)` **within that startup pass**, while still validating/installing every conversation's native binding before `harness.resume()` and before any denied-conversation abort enables scheduling (`runtime.ts:163–165`). This avoids repeated discovery without changing native authority restoration. It is an app optimization, not a free upstream feature. Lazy restoration would need a separate active-task/recovery design and is not recommended by this audit.

## Suggested next step

Start with startup model-registration deduplication and a small selection-context refactor; measure list hydration before changing catalog/storage plumbing. Preserve the native authority and publication boundaries. The strongest additional upstream reuse is lifecycle cancellation of observations; a wholesale replacement of the remaining bridge code would remove guarantees rather than duplicate ownership.

## Implementation amendment — selected-model provider factory

2026-10-16, ticket 01. Public `createProvider` now constructs both native-backed
providers and dispatches their distinct standard/simple upstream API wrappers.
The separate mutable catalog map was removed; selected models live in the
factory's static catalog. Native discovery still reads one explicitly selected
model. `fetchModels` was evaluated but adds machinery here: Pi 1.3.0 publishes a
provider-wide overlay and replaces records, requiring an identity adapter and
serialization to preserve resolved scheduler handles. The static factory retains
the supplied record references, so the retained `loadModel` adapter updates a
resolved record only after successful native discovery. Terminal native admission
follows the asynchronous observation. The catalog is read after discovery, so
concurrent distinct registrations merge; explicit registration reloads native
settings and invalidates the one-shot observation marker.

Focused fixtures verify identity across settings refresh, first-inference capacity
reaching the next standard Pi threshold-compaction decision, honest unknown limits
after failed discovery, and renewed observation following explicit invalidation.
A mixed startup fixture restores five valid native bindings while reducing five
model configuration reads to three distinct pairs; denied-conversation abort and
resume both follow all five bindings. A fresh startup repeats the three reads,
and discovery failure enables no scheduling. Provider/citation/compaction/startup
fixtures pass **64 tests**; focused TypeScript compilation passes. Desktop and
simulator acceptance remain with ticket 06. The original research above remains
historical evidence, not a claim that a dynamic factory supplies in-place refresh.
