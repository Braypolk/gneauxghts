# iOS on-device chat runtime research

**Historical investigation:** superseded on 2026-10-11 by the decision to use desktop-equivalent remote chat providers on mobile. Recommendations below describe the stopped experiment, not the active implementation plan.

Research date: 2026-10-11. Scope: recent iPhones, simulator first, no hosted fallback. This is source research and an experiment recommendation; runtime execution belongs in the subsequent probe validation record.

## Recommendation

Reuse the app's pinned **LiteRT-LM 0.18.0 CLiteRTLM framework**, already embedded for semantic search, and probe **Qwen3-0.6B's newer dynamic INT4 artifact** through its C Conversation API. The original default INT8 file remains useful as a measured text-generation baseline, but local metadata inspection below disqualifies its packaged defaults for the tool/thinking experiment. The tagged runtime exposes generation, role-based conversation input, asynchronous JSON-message streaming, cancellation and parsed function calls. There is no need to add a second inference framework before testing this route. [Tagged Conversation API](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/c/conversation.h), [tagged generation API](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/c/engine.h).

This establishes a practical experiment, not desktop chat parity. The converted model has a 4,096-token context and a small parameter count; the app's real preamble, tool declarations, selected notes, history and result formatter require their own fit and reliability checks. The original model supports thinking and non-thinking operation and tools, but those capabilities do not establish reliable vault evidence selection or proposal behavior in this application. [Conversion publisher](https://huggingface.co/litert-community/Qwen3-0.6B), [original Qwen model card](https://huggingface.co/Qwen/Qwen3-0.6B).

### Artifact metadata distinction discovered during execution

The parent simulator experiment reports that default INT8 produces text on CPU and Metal but emits raw thinking delimiters and prose suggesting tool calls, without parsed calls, despite disabling thinking. Local read-only inspection of the downloaded file explains a packaging mismatch worth isolating: its metadata protobuf at offset 16,384 contains only fields 1–5 (start/stop, legacy role affixes, sampler, 4,096-token capacity). It has no field 6 model type, field 7 Jinja template, or field 8 channels. The default file also contains no `enable_thinking` template variable. These are inspected bytes, not a general claim that Qwen weights cannot use tools. The current schema defines those missing fields, and explains how legacy role templates are retained for backward compatibility. [Tagged metadata schema](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/runtime/proto/llm_metadata.proto).

Publisher history reinforces the distinction: a July 17 thinking-template change to the default file was immediately reverted; the September 21 revision explicitly refreshes only the dynamic INT4 export with the newer content-parts template. The card links that template's source, which includes tool declarations, tool-call formatting, tool responses and an `enable_thinking` branch. Compare the hash-verified dynamic file before concluding tool feasibility. [Publisher commit history](https://huggingface.co/api/models/litert-community/Qwen3-0.6B/commits/main), [linked Qwen3 template](https://github.com/google-ai-edge/LiteRT-LM/blob/a8178d7dca6ac4d472476c9d76e482d8c8cbee3c/models/qwen3/LlmMetadataProto.pbtext).

The fully downloaded dynamic artifact's SHA-256 was independently checked against the pin above. Its embedded 3,020-byte Jinja template contains the tools preface and thinking branch, but **its `format_content` macro renders strings or parts with `type: text` only**. It silently omits `type: tool_response` parts. This differs from the current tagged Swift bridge and newer tagged Qwen template, which serialize those parts. Consequently the initial probe's Swift-style tool reply supplies an empty `<tool_response>` to this particular artifact. That round-trip failure is not yet evidence of model-quality failure. Send a `role: tool` message with a text part containing serialized tool-result JSON, and verify the native rendered message contains the fixture value before repeating inference. This finding comes from local inspection of the exact pinned binary, rather than assuming the linked source template equals its embedded template. [Pinned artifact](https://huggingface.co/litert-community/Qwen3-0.6B/resolve/a3c5d805ae362dff7f580bc25f2dfb9a5a7eaa76/Qwen3-0.6B_dynamic_wi4b32_afp32.litertlm), [newer tagged template for comparison](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/models/qwen3/LlmMetadataProto.pbtext).

`config_set_tools` merely stores tool JSON; it does not enable constrained decoding. The conversation builder's separate flag defaults to false. Enabling it constrains supported tool syntax, but cannot by itself replace absent Qwen metadata or establish correct tool selection. [C configuration implementation](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/c/conversation.cc), [builder defaults](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/runtime/conversation/conversation.h).

Runtime identity remains [CLiteRTLM.xcframework.zip v0.18.0](https://github.com/google-ai-edge/LiteRT-LM/releases/download/v0.18.0/CLiteRTLM.xcframework.zip), SHA-256 `d765b99592d4ec3d0c9e2bd69469454af06c834861340672da1891c0c121c347`. Retain the correct simulator/device slice and the existing build-time embedding and signing route. [Tagged Package.swift](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/Package.swift), [prior app packaging evidence](../../mobile-ios-readiness/app-semantic-validation.md).

## Concrete native probe contract

Create generation-engine settings using the model path and `cpu` or `gpu`, with vision/audio unset. Set a bounded engine context, four CPU threads for the first CPU experiment, and a writable cache directory. Create the engine, a session config with a bounded output-token count and deterministic sampler, then a conversation config. Disable thinking for the initial comparison; preserve model metadata/template. Engine and session limits are distinct, and the output limit includes thinking tokens. [Tagged engine settings/session API](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/c/engine.h).

**CPU sampler constraint discovered during the probe:** although the C enum exposes TopK (`1`), TopP (`2`) and Greedy (`3`), the tagged CPU sampler factory implements only unspecified and TopP. TopK and Greedy produce the observed `UNIMPLEMENTED: Sampler type: X not implemented yet`. C-to-protobuf mapping preserves these values, so this failure agrees with the tagged implementation rather than establishing an ABI mismatch. For deterministic output, create sampler type **TopP (`2`)**, then set `top_k=1`, `top_p=1.0`, `temperature=0.0`, and `seed=0`. The TopP CPU implementation accepts positive k, p in `[0,1]`, and nonnegative temperature. The sampler protobuf says the type field is ignored for GPU sampling, which combines top-k/top-p; this CPU diagnosis therefore does not explain a separate GPU hang. [Tagged sampler factory](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/runtime/components/sampler_factory.cc), [C enum conversion](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/c/engine.cc), [TopP validation](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/runtime/components/top_p_cpu_sampler.cc), [sampler protobuf](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/runtime/proto/sampler_params.proto).

Benchmark enablement has the one-argument signature `void litert_lm_engine_settings_enable_benchmark(LiteRtLmEngineSettings* settings)`; there is no boolean argument. Read conversation benchmark info after terminal delivery and release its owned handle. [Tagged C benchmark API](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/c/engine.h), [conversation benchmark API](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/c/conversation.h).

The C conversation config supports system content, initial messages, tools and extra template context. **`litert_lm_conversation_config_set_system_message` accepts content**, not a whole role/message object: the implementation supplies `role: system`. Pass a JSON text-parts array, for example `[{"type":"text","text":"Be concise."}]`. Initial history is a message array. Keep the native engine/library alive beyond every conversation and callback. [Tagged config implementation](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/c/conversation.cc).

Use these canonical message and tool shapes in the probe:

```json
{"role":"user","content":[{"type":"text","text":"Look up the synthetic note."}]}
```

```json
[{"type":"function","function":{"name":"lookup_note","description":"Read the synthetic note fixture.","parameters":{"type":"object","properties":{"key":{"type":"string"}},"required":["key"]}}}]
```

```json
{"tool_calls":[{"type":"function","function":{"name":"lookup_note","arguments":{"key":"fixture"}}}]}
```

```json
{"role":"tool","content":[{"type":"text","text":"{\"body\":\"The test project is called Cedar.\"}"}]}
```

Tool arguments are JSON objects in parsed calls. The app executes them; native generation does not confer write permission. The text-part reply above is specific to the inspected artifact. The tagged Swift bridge instead supplies `{"role":"tool","content":[{"type":"tool_response","name":"lookup_note","response":{"body":"..."}}]}`; use that only with a template that renders such parts. Default message normalization preserves part types, so it does not rescue a `tool_response` part omitted by Jinja. Send a second synthetic non-executable result-formatting tool to test the application's structured-output pattern, rather than treating a valid prose answer as sufficient. [Tagged tool-use guide](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/docs/api/cpp/tool-use.md), [tagged Swift tool bridge](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/swift/Conversation.swift), [message normalization](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/runtime/conversation/model_data_processor/data_utils.cc).

`litert_lm_conversation_send_message_stream` returns a start status and invokes its callback from a background thread. Read chunk text/error/final through the chunk accessors and copy data during the callback. Conversation chunk text contains a JSON **message fragment**, not plain generated prose. Text parts, thought channels and tool calls need separate handling. With tool-token streaming disabled, complete parsed `tool_calls` are emitted after buffering; this is the simplest initial probe mode. Never execute partial tool JSON. [C conversation API](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/c/conversation.h), [tool streaming behavior](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/docs/api/cpp/tool-use.md).

Cancellation requires extra care: `CancelProcess` poisons the underlying session, and **subsequent calls on that conversation are unsupported**. Wait for terminal cancellation delivery, destroy that conversation, and reconstruct a new one from admitted app history before retrying. The C wrapper maps both an error and the normal empty end marker to terminal chunks; cancellation has an error string. Do not release callback userdata or the engine as soon as the cancel function returns. The source promises cancellation delivery, but does not provide a bounded stop-latency guarantee; measure it. [Tagged conversation lifecycle contract](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/runtime/conversation/conversation.h), [native callback propagation](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/runtime/conversation/internal_callback_util.cc), [C terminal mapping](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/c/conversation.cc).

**A terminal flag is not a callback-drain guarantee.** The tagged C wrapper marks every parser error `is_final=true` without suppressing later calls. The native streaming helper's `SendMessage` forwards a `ToMessage` error through the callback but returns `void`; the caller can continue processing and later issue another error or the ordinary empty completion marker. `SendCompleteMessage` also flushes remaining text before independently parsing the complete response. A truncated/malformed tool sequence can therefore deliver multiple chunks marked final. Latch the first terminal application outcome, reject any later content from that attempt, and count later native callbacks as diagnostics. Releasing callback userdata on the first final chunk risks a use-after-free. [Native streaming helper](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/runtime/conversation/internal_callback_util.cc), [C wrapper](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/c/conversation.cc).

For the isolated probe, retain every stream callback allocation until **all conversations and the engine have been destroyed**. The source supports this stronger lifetime: session destruction waits for session tasks; engine destruction waits for all execution and callback work, then destroys the execution manager; its thread-pool destructors join worker threads. Session deletion alone exposes no C-level callback-drain result. Perform cleanup on the owning worker, never inside a native callback that could join itself. This is an implementation-derived cleanup policy, not a bounded-latency promise: the native default wait is ten minutes and destructor paths can ignore/log wait errors. A production retained-engine adapter still needs an explicit, tested callback-ownership/draining design rather than copying a first-final release pattern from a language wrapper. [Session destructor](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/runtime/core/session_advanced.cc), [engine destructor](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/runtime/core/engine_advanced_impl.cc), [execution-manager cleanup](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/runtime/framework/resource_management/threaded_execution_manager.cc), [thread-pool join](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/runtime/framework/threadpool.cc), [native default timeout](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/runtime/engine/engine.h).

Constrained decoding has two separate upstream routes: tool-call syntax constraints, or custom LLGuidance output constraints. The C API exposes enabling tool constraints and selecting LLGuidance plus per-turn regex/JSON-schema constraints. Test availability in the shipped binary rather than assuming an exported setter proves successful decoding. Syntax constraints cannot certify correct evidence or an appropriate proposal. [Tagged constrained-decoding guide](https://raw.githubusercontent.com/google-ai-edge/LiteRT-LM/v0.18.0/docs/api/cpp/constrained-decoding.md).

## Application seam and acceptance

The current `AgentProvider::Local` enters `ensure_local_desktop()` and constructs an OpenAI-compatible HTTP client using `local_base_url`. It is not an in-process mobile provider. Provider construction and translation belong inside `agent_runtime.rs`; `ChatService` continues owning durable runs, events, context and proposal status. Implementing a provider may extend settings/capability mapping, but must preserve that ownership. [Current agent runtime](../../../src-tauri/src/agent_runtime.rs), [accepted ADR 0001](../../../docs/adr/0001-keep-agent-runtime-app-owned.md).

A production adapter should translate native messages into the existing app-owned runtime stream while retaining tool concurrency, guard/deadline checks, evidence validation, permission admission and proposal review. The existing `configured_builder` requests structured results through `OutputMode::Tool`, and `result_stream.rs` handles transient result-formatter arguments. Replacing this with unvalidated raw model text would change the application's result contract. [Runtime builder and driver](../../../src-tauri/src/agent_runtime.rs), [result stream owner](../../../src-tauri/src/agent_runtime/result_stream.rs), [behavior invariants](../../../docs/architecture/behavior-invariants.md).

Run the first experiment in an isolated simulator app with synthetic notes only:

1. Verify native generation symbols and model digest. Run CPU and Metal in separate fresh launches and retain failures as evidence.
2. Record cold/cached engine initialization, first visible chunk, completion, native token count, output ceiling, process footprint and post-close footprint. Use short and progressively longer context; enforce a wall deadline.
3. Exercise a multi-turn conversation, synthetic read-tool round trip, result formatter, malformed/unknown tool request rejection, and incomplete/truncated output. Validate both schema and expected fixture values.
4. Cancel during generation, measure terminal delivery, recreate the conversation, and successfully retry. Include missing-model and invalid-model initialization failures.
5. Before product integration, measure the actual app preamble/tool/result-schema token count against the artifact's context. Reserve space for tool results and output; refuse oversize requests rather than silently removing policy or evidence.
6. Later test the real app's chat persistence, context access, reviewed proposal acceptance/rejection, background/interruption recovery and coexistence with semantic indexing. Simulator-only inference cannot close these acceptance items.

Until physical measurements exist, serialize inference in the probe and avoid asserting that simultaneous chat and semantic engines fit. Model file size is not resident memory or an iPhone process allowance. Device acceptance needs full-app plus WebKit footprint, available headroom, sustained decode/prefill, thermals, suspension and memory-pressure recovery. Apple's available-memory API is advisory and changes during process life. [Apple `os_proc_available_memory`](https://developer.apple.com/documentation/os/os_proc_available_memory), [existing device gate](../../mobile-ios-readiness/issues/08-ios-device-release-gate.md).

No llama.cpp comparison is needed for this first decision: the existing bundled runtime supplies the required native API surface, so testing it avoids introducing another runtime/model format before any observed blocker. Reopen that comparison if this exact artifact/runtime fails measured quality, context, platform or resource gates. No hosted provider is selected automatically when local inference fails.
