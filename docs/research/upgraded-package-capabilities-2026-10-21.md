# Useful capabilities after the dependency upgrades — 2026-10-21

This revisits the six items in the original [dependency refresh](dependency-refresh-2026-10-21.md#useful-capabilities-to-consider) against the application we actually have, including the subsequent Kit 3, WDIO 10, Bits UI/Vitest and CodeMirror/Lezer upgrades. This records the pre-implementation research and priorities. Ready items have since been implemented or evaluated; the [implementation outcome](../../.scratch/archive/package-capabilities-2026-10-21.md) records actual results and verification limits. The separate image chat owns image changes and their evidence.

The installed graph is the boundary: Svelte 5.57.2, Kit 3.1.0, Svelte Vite plugin 7.3.1, Vite 8.3.5, Bits UI 2.20.0, Vitest 5.0.5, WDIO 10.1.0, CodeMirror commands 6.11.1/view 6.43.15/language 6.13.1, Lezer common 1.5.3/Markdown 1.8.1, Rust Tauri 2.12.5, reqwest 0.13.5, Tantivy 0.27.0, tokio-util 0.7.20, base64 0.23.1, notify 8.2.0 and regex 1.13.1. Manifests and both lockfiles establish versions. Features of retained or unreleased versions are excluded.

## Recommendation

The original first priorities were **curated connection failure categories** and **repeatable benchmark comparisons**; both are now implemented. Both address concrete gaps without changing product semantics. Enable **component-stack inspection** as a development aid. Investigate **image delivery** with measurements before selecting a transport, and compare **token-aware search excerpts** with the existing query-centered previews. The [implementation plan](../../.scratch/package-capabilities/spec.md) records the subsequent call-site audit, safe initial scopes and conditional follow-ups.

Priorities below are judgments based on current call sites. Effort is relative, not a delivery estimate. A newly exported API is not automatically a worthwhile feature.

| Suggested order | Work | Payoff | Effort |
| --- | --- | --- | --- |
| 1 | Classify DNS, connection and timeout failures | Actionable setup/chat explanations rather than one generic failure | Small–medium |
| 2 | Save and compare Vitest benchmark results | More reliable evidence for future editor performance changes | Small–medium |
| 3 | Make the Svelte component-stack inspector easy to opt into | Faster navigation from visible UI to its owning component | Small |
| 4 | Add Kit 3 client error presentation | Clearer diagnostics; recovery remains a separate ownership design | Medium |
| 5 | Measure and improve native image delivery | Potentially less UI blocking, IPC copying and memory overhead | Medium, evidence first |
| 6 | Compare token-aware canonical excerpts with current previews | Establish whether snippet scoring adds value beyond existing query centering | Medium, product experiment |

The [frontend capability report](upgraded-frontend-capabilities-2026-10-21.md) contains source-backed details for the frontend and testing rows, plus lower-priority options.

### 1. Better connection errors: high value, small to medium effort

Reqwest 0.13.5 adds `Error::is_dns()`. At the initial audit, `pi_chat/transport.rs::dispatch` discarded the request error and returned the same `connection` result for every send failure. The implemented classifier now distinguishes timeout, DNS and broad connection failures with fixed safe copy; the [archived execution ticket](../../.scratch/archive/package-capabilities-2026-10-21/tickets/01-connection-errors.md) records the scope and focused acceptance. HTTP rejection already has a separate curated classification. [Reqwest 0.13.5 release notes](https://github.com/seanmonstar/reqwest/blob/v0.13.5/CHANGELOG.md).

Add a small native classifier before converting to `DomainError`; preserve the existing HTTP, credential, cancellation and authority paths. DNS is the newly available discriminator; timeout/connect helpers already existed. Inspect DNS before the broader connect category. Do not infer “offline” from DNS alone, expose raw error strings/URLs, or add automatic retries to requests that may have effects. Model metadata currently returns `Option` on failure, so a Settings explanation would need an explicit result path rather than just changing the streaming transport.

Relevant code: [native transport](../../src-tauri/src/pi_chat/transport.rs), [model metadata](../../src-tauri/src/provider_config/model_metadata.rs), and the native provider adapter under [chat Pi](../../src/lib/features/chat/pi/). Acceptance: controlled unresolved-host, refused-loopback, timeout, cancellation and HTTP-auth cases produce distinct safe explanations, with no secret/endpoint leakage and unchanged recovery behavior.

### 2. Image delivery: promising, measure first, medium effort

Tauri 2.12 provides asynchronous asset-protocol handling. The installed published `tauri-2.12.5/src/protocol/asset.rs` implements the handler through `async_runtime::spawn` and asynchronous filesystem reads; this agrees with the upstream [Tauri changelog](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri/CHANGELOG.md). At the initial audit the app did **not** use this path for editor images: `read_image_asset_data_url` synchronously read/base64-encoded bytes through the document-owned loader. This paragraph describes that baseline; the [separate image implementation report](tauri-async-images-2026-10-21.md) records the later selected transport and current behavior. An allowed `asset:` CSP entry alone does not enable or scope that protocol.

There are two experiments worth comparing: move existing reads/encoding onto blocking workers while preserving the data-URL contract, or deliver admitted images through a narrowly scoped native asset URL. The former does not require a newly added package API. The latter can avoid base64/IPC string copies, but needs deliberate protocol enablement, scope and lifetime/cache design. Retain `asset_paths.rs` containment checks, Running Vault ownership, root-aware cache keys, fingerprints, bounded cache behavior and replacement/destroy handling. Do not grant the entire filesystem or treat a converted URL as authorization.

Relevant code: [asset commands](../../src-tauri/src/commands/asset_commands.rs), [asset containment](../../src-tauri/src/asset_paths.rs), [document resources](../../src/lib/features/notepad/editor/editorDocumentResources.ts), [image loader](../../src/lib/features/notepad/images/imageAssetLoader.ts), [Tauri configuration](../../src-tauri/tauri.conf.json). Acceptance: compare cold/warm image-heavy note opening, IPC bytes, memory and native input responsiveness; test cross-vault replacement, image modification, traversal/symlink escapes and stale completions. Avoid a broad loader rewrite without measurable benefit.

### 3. Search excerpts: useful product experiment, medium effort

Tantivy 0.27 adds `Snippet::fragment_range()`, parser support for exists queries, generated tie-breaker fields and additional collection/query tools. Its top-K improvements are internal, not evidence of a particular app speedup. [Tagged Tantivy changelog](https://github.com/quickwit-oss/tantivy/blob/0.27.0/CHANGELOG.md).

The later planning audit established that ordinary all-notes Search and Pi search already use `search.rs::build_search_preview` to center on literal query/term matches; current-note Search crops around occurrences too. The prefix-only path in `services/retrieval/search.rs` belongs to `retrieval_context`, whose frontend wrapper currently has no production caller. Improving that unused path alone is not a user-facing win. The completed [bounded experiment](search-excerpt-experiment-2026-10-21.md) compared token-aware snippet scoring against the existing previews. It retained the current algorithm: distributed-term clusters improved, but Unicode context/cropping failed the no-regression gate. The installed snippet source documents **UTF-8 byte offsets into the supplied text**; for `snippet_from_doc`, values are joined and trimmed. Therefore an indexed fragment range is not automatically an editor position. Existing frontend highlights use code points and editor positions use UTF-16. Keep those conversions explicit.

Relevant code: [lexical candidates](../../src-tauri/src/lexical.rs), [canonical search owner](../../src-tauri/src/services/retrieval/search.rs), [current-note coordinate conversion](../../src/lib/features/notepad/search/currentNoteSearch.ts). Acceptance: late matches, emoji/combining marks, repeated paragraphs, pending index work, external changes and excluded notes; navigation must still revalidate canonical content. Keep semantic-only result previews meaningful. This improves presentation, not citation authority.

Generated tie-breakers are segment-local sequences with random starting offsets, preserved across merges; they do not establish stable Note Identity ordering across an in-memory index rebuild. Existing retrieval already breaks final ties by passage identity. New query/sort modes need a product requirement and appropriate fields, not a default schema change. Experimental calculated fields/JIT and analytical aggregations have no demonstrated need here.

### 4. Selection history: defer until there is a distinct feature

Commands 6.11.0 added `canUndoSelection` / `canRedoSelection`, available in installed 6.11.1. They answer whether `undoSelection` / `redoSelection` can run, not whether a text edit can be undone. Ordinary history has the older `undoDepth` / `redoDepth` helpers. [Published commands changelog](https://code.haverbeke.berlin/codemirror/commands/src/tag/6.11.1/CHANGELOG.md).

The app routes Undo/Redo through [EditorDocumentRuntime](../../src/lib/features/notepad/editor/editorDocumentRuntime.ts) and [editor shortcuts](../../src/lib/features/notepad/editor/editorShortcuts.ts), with a headless shared history root and pane-local selection/view state. There is no current selection-history command to enable. A future Back/Forward Selection feature must define whether navigation belongs to each pane, without adding duplicate document undo histories. Ordinary Undo menu state should come from the document history owner.

Language 6.12.4 also makes bulk `foldEffect` range building linear. This is automatically available **if** the corresponding CodeMirror folding extensions are used; the app currently uses custom visible Markdown decorations, and no `codeFolding`, `foldEffect`, `foldGutter` or `foldAll` call sites were found. Do not attribute custom marker-hiding speed to that fix. [Published language changelog](https://code.haverbeke.berlin/codemirror/language/src/tag/6.13.1/CHANGELOG.md).

### 5. Tokio task cleanup: preserve explicit lifetimes

Tokio-util 0.7.19 adds nongeneric `AbortOnDrop`, available under the enabled `rt` feature. It wraps an `AbortHandle` and aborts on drop; unlike the older `AbortOnDropHandle`, it cannot be awaited for the task result. The 0.7.20 cancellation-token notification fix is already received by updating. [Tagged tokio-util changelog](https://github.com/tokio-rs/tokio/blob/tokio-util-0.7.20/tokio-util/CHANGELOG.md), [published task source](https://docs.rs/crate/tokio-util/0.7.20/source/src/task/abort_on_drop.rs).

Use the new wrapper only for truly disposable spawned observation tasks. Native transport already has explicit cancellation and a settled-request drain; watcher workers are owned OS threads with stop/join. An abort guard cannot replace either contract. Pane switches must not cancel Pi work, and restart must still join effects before closing storage. There is no demonstrated orphan-task bug that warrants a lifecycle refactor. See [architecture](../../ARCHITECTURE.md) and [behavior invariants](../architecture/behavior-invariants.md).

## Additional frontend/testing opportunities

Vitest 5 offers paired `bench.compare` measurements, saved `writeResult` output, `bench.from` baselines and relative assertions. The existing six parser/image workloads already use the migrated benchmark fixture; adding comparisons is the remaining opportunity. Record machine/runtime/fixture/package versions and keep native focus/frame tests separate. Its `doctor` command can also measure alternative worker configurations before changing isolation or concurrency. Filesystem module caching is already enabled by default. [Benchmark guide](https://vitest.dev/guide/benchmarking), [doctor command](https://vitest.dev/guide/cli#vitest-doctor).

Kit 3 sends child rendering failures through client error handling and route error boundaries. The implemented synchronous `hooks.client.ts` and plain `+error.svelte` now provide curated diagnostics and a selectable local reference without adding a server; [the outcome record](../../.scratch/archive/package-capabilities-2026-10-21.md) records completed browser/unit/native acceptance and its ownership limits. The root layout is outside that route boundary; replacing a failed child tears down its workspace. The initial plan therefore omits recovery controls. Safe remount/restart must first establish draft/owner settlement; automatically reloading an editable workspace is not an acceptable default. [Kit error migration](https://svelte.dev/docs/kit/migrating-to-sveltekit-3#Error-handling).

The original Svelte helper suggestion is modest: `SvelteMap.getOrInsertComputed` can simplify a genuine lazy insertion, and the new third `[get, set, has]` context function can preserve optional-provider behavior with shared types. `createContext` itself predates this upgrade. The typed optional context was adopted. Related insertion remains explicit because Svelte's server/default export aliases native Map and Node 24.2 lacks `getOrInsertComputed`; all existing Related lifetime tests pass. These APIs do not make map values deeply reactive or replace subscription/consumer lifetime management. One scoped `vi.when` pilot now registers exact ID/path tuples while preserving its deferred promises; no general mock rewrite was made. Current seams, exact versions and owning sources are documented in the [frontend report](upgraded-frontend-capabilities-2026-10-21.md).

Floating UI's new layout-viewport boundary is a targeted option for a reproduced positioning issue, not a global improvement: visible-area collision handling matters around software keyboards. Bits UI's fixes benefit the primitives actually used here; native HTML selects do not receive Bits Select fixes, and no RadioGroup consumer needs its new autocomplete option. WDIO AI actions would require an additional model/provider setup and compatibility proof; the requested deterministic verification loop is already present. Vite and Tailwind gains mostly arrive automatically for the installed ranges. See the [frontend report](upgraded-frontend-capabilities-2026-10-21.md) for the call-site audit and primary sources.

## Benefits already obtained and ideas to leave alone

The recent editor upgrade already supplies block-group reuse, mixed-tree scanning improvements, and native scrolling/composition/widget fixes. These require no new app feature; measured results and limitations are in the [editor upgrade report](codemirror-lezer-upgrade-2026-10-21.md). WDIO persistent sessions, evidence and deterministic test export are already implemented; additional testing opportunities are in the [frontend investigation](upgraded-frontend-capabilities-2026-10-21.md).

Tauri channel delivery after a JS callback throws and macOS restart relaunch fixes benefit existing channels/restart automatically. Its new core exit API does not replace this app's coordinated restart, and its launch-activation option is not sufficient reason to change the already explicit background/foreground test policy. Portable app-directory overrides, new fullscreen/Glass presentation, additional resource-disposal syntax and broad watcher symlink policy changes should wait for a concrete requirement. [Tauri 2.12 notes](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri/CHANGELOG.md).

The image, compression/archive, hashing, serialization and loader updates primarily provide correctness, compatibility and maintenance improvements for current usage. `image` buffer-copy improvements and Markdown parsing fixes do not imply new image formats or a new Markdown dialect. `diff` 9 patch APIs are unrelated to the current `diffArrays` review highlighter; keep its bounded comparison/fallback behavior. Pi/Chord were already current and do not supply newly unlocked capabilities in this refresh. Further SQLite, Rust toolchain or syn upgrades remain separate work. See the [native audit](dependency-refresh-rust-2026-10-21.md), [runtime audit](dependency-refresh-runtime-2026-10-21.md) and [retained-version review](retained-dependency-review-2026-10-21.md).

## Evidence limits

Research checked current call sites, installed published distribution/changelog/source files, lockfiles and first-party upstream documentation. Some web mirrors lag the installed package versions or could not serve their tagged pages; version-specific local published sources were used in those cases, especially CodeMirror/Lezer, Tauri and snippet offset semantics. Recommendations are inferences from those sources. This original research phase performed no runtime acceptance. Subsequent implementation, bounded measurements and current acceptance limits are recorded separately in the [outcome](../../.scratch/archive/package-capabilities-2026-10-21.md).
