# AFFiNE realtime collaboration

Research date: 2026-10-19. Scope: source-code inspection of the `canary` branch at commit [`0b69a6da21e8fd35beb85667bb8496d9b3852238`](https://github.com/toeverything/AFFiNE/tree/0b69a6da21e8fd35beb85667bb8496d9b3852238). These are implementation observations, not an installed-app test or a claim about every deployed release. Current code matters: older AFFiNE descriptions and protocol examples can differ from this branch.

## Core design

AFFiNE synchronizes Yjs CRDT document updates through a local storage/sync layer called `nbstore`. The frontend watches a `Y.Doc`'s `update` event, queues changes for local storage, and applies incoming storage updates with Yjs `applyUpdate`. A dedicated origin (`nbstore-frontend`) prevents those received updates from being saved back as fresh local edits. [Frontend document adapter](https://github.com/toeverything/AFFiNE/blob/0b69a6da21e8fd35beb85667bb8496d9b3852238/packages/common/nbstore/src/frontend/doc.ts)

The important architectural distinction is that editing updates the local document and persistence first, while synchronization operates on that stored state. The cloud adapter exchanges binary Yjs updates encoded as base64 inside application-specific Socket.IO messages. This is a server-mediated design; the examined cloud path does not establish peer-to-peer browser connections. [Frontend document adapter](https://github.com/toeverything/AFFiNE/blob/0b69a6da21e8fd35beb85667bb8496d9b3852238/packages/common/nbstore/src/frontend/doc.ts), [Cloud document storage](https://github.com/toeverything/AFFiNE/blob/0b69a6da21e8fd35beb85667bb8496d9b3852238/packages/common/nbstore/src/impls/cloud/doc.ts)

## End-to-end update flow

1. A local edit generates a Yjs update, which `nbstore` queues and writes to local storage. [Frontend adapter](https://github.com/toeverything/AFFiNE/blob/0b69a6da21e8fd35beb85667bb8496d9b3852238/packages/common/nbstore/src/frontend/doc.ts)
2. A client connects using Socket.IO and joins its workspace/document subscriptions with `space:join-batch`. Cloud connections prefer WebSocket only; the self-hosted path enables polling and WebSocket transports. [Socket connection](https://github.com/toeverything/AFFiNE/blob/0b69a6da21e8fd35beb85667bb8496d9b3852238/packages/common/nbstore/src/impls/cloud/socket.ts), [Sync gateway](https://github.com/toeverything/AFFiNE/blob/0b69a6da21e8fd35beb85667bb8496d9b3852238/packages/backend/server/src/core/sync/gateway.ts)
3. `space:push-doc-update` carries the update to the server. The gateway checks the active subscription and `Doc.Update` authorization, awaits the storage/runtime append, then publishes the update and acknowledges acceptance with a timestamp. Workspace root updates take a separate domain-command path. [Sync gateway](https://github.com/toeverything/AFFiNE/blob/0b69a6da21e8fd35beb85667bb8496d9b3852238/packages/backend/server/src/core/sync/gateway.ts)
4. The gateway emits `space:broadcast-doc-updates` to other active subscribers to that document. The broader workspace room receives `space:broadcast-doc-invalidation` with a timestamp, rather than every document's full payload. The gateway can merge several Yjs updates into one before broadcasting. [Sync gateway](https://github.com/toeverything/AFFiNE/blob/0b69a6da21e8fd35beb85667bb8496d9b3852238/packages/backend/server/src/core/sync/gateway.ts)
5. Receiving clients persist/apply the incoming update to their local document. The frontend delegates the actual merge to Yjs `applyUpdate`; it does not implement a text-operation transformation algorithm in this adapter. [Cloud document storage](https://github.com/toeverything/AFFiNE/blob/0b69a6da21e8fd35beb85667bb8496d9b3852238/packages/common/nbstore/src/impls/cloud/doc.ts), [Frontend adapter](https://github.com/toeverything/AFFiNE/blob/0b69a6da21e8fd35beb85667bb8496d9b3852238/packages/common/nbstore/src/frontend/doc.ts)

## Initial sync and reconnect

The `DocSyncPeer` pull-and-push job derives a Yjs state vector from the locally stored document, then requests `space:load-doc` through `remote.getDocDiff`. The server returns its missing update, its own state vector, and a timestamp. The client writes the returned update locally, computes the local changes missing on the server, and pushes those back. This avoids requiring a complete document upload/download for every reconciliation. The worker also has retry scheduling; the inspected error path waits five seconds before another attempt. [Document sync peer](https://github.com/toeverything/AFFiNE/blob/0b69a6da21e8fd35beb85667bb8496d9b3852238/packages/common/nbstore/src/sync/doc/peer.ts), [Cloud storage protocol](https://github.com/toeverything/AFFiNE/blob/0b69a6da21e8fd35beb85667bb8496d9b3852238/packages/common/nbstore/src/impls/cloud/doc.ts), [Server diff calculation](https://github.com/toeverything/AFFiNE/blob/0b69a6da21e8fd35beb85667bb8496d9b3852238/packages/backend/server/src/core/doc/storage/doc.ts)

**Inference:** this local-first reconciliation path is what allows edits made while disconnected to catch up when connectivity returns. The state vector is a summary of CRDT knowledge; the timestamps tracked alongside it are sync bookkeeping, not a substitute for CRDT conflict resolution. This inference follows the explicit state-vector/diff exchange above. [Document sync peer](https://github.com/toeverything/AFFiNE/blob/0b69a6da21e8fd35beb85667bb8496d9b3852238/packages/common/nbstore/src/sync/doc/peer.ts)

## Persistence and multiple servers

The backend uses PostgreSQL. Its schema explicitly models the current document as a `Snapshot` plus `Update` rows, with binary payloads, and provides `SnapshotHistory` separately. Reading a document merges its snapshot and pending updates; a transaction writes the new snapshot, optionally creates history, and marks the old updates merged. Thus the server keeps durable CRDT state rather than only relaying live traffic. [Database schema](https://github.com/toeverything/AFFiNE/blob/0b69a6da21e8fd35beb85667bb8496d9b3852238/packages/backend/server/schema.prisma), [Storage merge/snapshot logic](https://github.com/toeverything/AFFiNE/blob/0b69a6da21e8fd35beb85667bb8496d9b3852238/packages/backend/server/src/core/doc/storage/doc.ts), [PostgreSQL workspace adapter](https://github.com/toeverything/AFFiNE/blob/0b69a6da21e8fd35beb85667bb8496d9b3852238/packages/backend/server/src/core/doc/adapters/workspace.ts)

For multiple backend instances, the Socket.IO adapter uses `@socket.io/redis-adapter`. An internal event bus uses `serverSideEmit` to propagate document updates, awareness events, and permission changes across the cluster; each gateway delivers updates to its local document subscribers. Redis is part of cluster fan-out here, while the cited PostgreSQL tables hold document state. [Socket.IO adapter](https://github.com/toeverything/AFFiNE/blob/0b69a6da21e8fd35beb85667bb8496d9b3852238/packages/backend/server/src/base/websocket/adapter.ts), [Event bus](https://github.com/toeverything/AFFiNE/blob/0b69a6da21e8fd35beb85667bb8496d9b3852238/packages/backend/server/src/base/event/eventbus.ts), [Sync gateway](https://github.com/toeverything/AFFiNE/blob/0b69a6da21e8fd35beb85667bb8496d9b3852238/packages/backend/server/src/core/sync/gateway.ts)

## Presence and permissions

Awareness is a separate transient channel: `space:load-awarenesses` asks active document clients to report their state; `space:update-awareness` is relayed as `space:broadcast-awareness-update`, including across backend instances. These handlers relay the awareness payload rather than appending it to document storage. **Inference:** presence/cursor-like state can disappear and be recollected independently of durable document content. [Awareness handlers in the sync gateway](https://github.com/toeverything/AFFiNE/blob/0b69a6da21e8fd35beb85667bb8496d9b3852238/packages/backend/server/src/core/sync/gateway.ts)

Socket establishment authenticates an existing cookie session or a JWT supplied in handshake auth. Joining checks `Workspace.Sync`, resolves document `Doc.Read`/`Doc.Update` permissions, and records a permission generation for the subscription. Permission-change events trigger subscription revalidation, and document loads/writes use the generation to avoid using stale authorization. The userspace path restricts access to the current user's own space. [Authentication guard/provider](https://github.com/toeverything/AFFiNE/blob/0b69a6da21e8fd35beb85667bb8496d9b3852238/packages/backend/server/src/core/auth/guard.ts), [Sync authorization](https://github.com/toeverything/AFFiNE/blob/0b69a6da21e8fd35beb85667bb8496d9b3852238/packages/backend/server/src/core/sync/gateway.ts)

## Limits of this investigation

These sources establish the architecture and concrete message flow. They do not establish production latency, concurrency limits, deployment topology, end-to-end encryption, or the exact visible outcome of every simultaneous semantic edit. No live collaboration session or failure-injection test was run.

Checked 2026-10-19. Public issue reports show recurring editing/scrolling problems as documents grow or accumulate complex blocks. They are self-selected reports, not a representative user survey. None establishes a universal safe document size; character count, block count, embedded frames, equations, canvas content, platform and release all matter. The strongest quantitative evidence found is a [July 29, 2026 user measurement](https://github.com/toeverything/AFFiNE/issues/14333#issuecomment-5120685969) on self-hosted Windows desktop 0.27.3. Thirty sequential CDP-injected keystrokes gave median renderer acknowledgement times of 9, 25 and 37 ms for different page-mode documents with 10, 101 and 170 blocks; a 510-block edgeless board measured 2,083 ms. Style recalculation plus layout accounted for about 1,970 ms per keystroke in that board, while backend activity was idle. The author explicitly could not compare the same document across both modes. This is a detailed single-user experiment, not an AFFiNE benchmark, universal limit, or proof that CRDT/network synchronization causes the lag.

Assessment: the merged selection fix is meaningful evidence of improvement work, but the cited later reports do not support declaring long/complex-document performance solved. For long plain-text notes, the evidence is mixed and weaker than the especially poor canvas/embedded-frame cases. Test representative documents on the intended release and platform before relying on AFFiNE for a large-note workflow; no trustworthy maximum word count follows from these sources.

## AFFiNE editor cost versus Yjs cost

The most useful distinction is **continuous editing/rendering latency** versus **CRDT loading, merging and encoding cost**. In the AFFiNE board measurement above, about 1,970 of 2,083 ms per keystroke was browser style/layout work, while JavaScript execution was about 60 ms. **Inference:** that particular stall was dominated by AFFiNE/BlockSuite's editor/browser rendering path, not by Yjs merge computation. This does not isolate the cost of Yjs on every AFFiNE document, and the benchmark used different documents in page and edgeless modes. [Measured AFFiNE report](https://github.com/toeverything/AFFiNE/issues/14333#issuecomment-5120685969)

Yjs itself is designed to avoid representing ordinary text as one JavaScript object per character. Consecutive compatible characters share an `Item`; nearby insert-position lookups use search-marker caching; deletion GC can discard deleted content. Its maintainer explains why editing history and data representation matter alongside visible document length. Consequently, “long note” alone is a poor predictor of CRDT cost. [Yjs internals](https://github.com/yjs/yjs/blob/main/INTERNALS.md), [Maintainer explanation](https://blog.kevinjahns.de/are-crdts-suitable-for-shared-editing)

Yjs has its own real scaling limits and pathological cases:

- **Large full-state application:** a November 2024 board report measured roughly 1.3–1.8 seconds applying an approximately 8.97 MB v1 update on an M3/Node 18 setup. The maintainer described that order of parsing cost as expected for a complex edited document and recommended workers for heavy server workloads. This concerns reconstructing full CRDT state, not the latency of every subsequent single-character edit. It is not a 5 MB or 9 MB universal cutoff. [Yjs #675](https://github.com/yjs/yjs/issues/675)
- **Many historical client IDs:** a 2022 synthetic test with Yjs 13.5.33 and 1,000 previous clients reported approximately 2.1 microseconds per operation without rotation versus 148 microseconds with rotation. This is historical evidence that state-vector/client history can matter; it is not a current AFFiNE measurement or a claim about 1,000 simultaneous users. [Yjs #415](https://github.com/yjs/yjs/issues/415)
- **Heavy GC and tombstones:** a 2023 large-update GC case on 13.6.4 reported 38 seconds versus 1.6 seconds without GC. A maintainer subsequently published an optimization in 13.6.7 and measured a reduction from 45 to nine seconds on the reproduction. Separately, a 2025 report on 13.6.27 involved about ten million deleted map entries and hundreds of MB of state; its author later said an application-side endless-loop bug generated the pathological data. These demonstrate real workload-specific risks, not ordinary long-note behavior. [Yjs #541](https://github.com/yjs/yjs/issues/541), [Yjs #741](https://github.com/yjs/yjs/issues/741)

The maintainer's [CRDT benchmarks](https://github.com/dmonad/crdt-benchmarks) explicitly distinguish operation replay, serialized size, encoding, parsing and memory, including a real editing trace repeated 100 times. Those results measure the data layer, not AFFiNE's DOM layout or typing experience. No new benchmark was run here. Overall inference: the reported AFFiNE per-keystroke stalls are stronger evidence of editor/integration performance problems than an inherent inability of Yjs to handle long prose, while large or historically complex CRDT states can still make loading/sync expensive.

## Gneauxghts comparison: existing evidence and limits

This comparison and the following design investigation are historical, from
before the formatting, inventory and draft-body improvements. Current outcomes
are recorded in the [draft-body migration](../../.scratch/archive/immutable-draft-bodies.md)
and its [native app benchmark](../../.scratch/archive/draft-body-app-benchmark/README.md).
They still do not establish a matched performance comparison with AFFiNE.

Inspected the current working tree on 2026-10-19 and ran the existing decoration microbenchmark, without running a new mounted application benchmark. Existing Gneauxghts evidence is encouraging for a moderate Markdown note, but it does not establish a speed ratio against AFFiNE or acceptance for multi-megabyte notes.

- **Measured opening/restoration:** the October 2 formatting investigation records a 220-section Markdown fixture with headings, emphasis, strike and links. After its presentation correction, final long-note navigation-to-visible-content samples were 19.4–27.3 ms; named samples were 24.1 ms for deep cursor restoration, 24.4 ms for restored scroll with delayed background parsing, and 19.7 ms for a chat-to-note remount. These were historical Chromium browser-harness measurements with a mocked backend; native WebKit was explicitly not measured. They concern first visible formatted content, not sustained typing or cold disk reads. [Investigation](../../.scratch/note-formatting-load/issues/01-formatting-before-readiness.md), [Current fixture/regression](../../e2e/specs/browser/editor-formatting-load.spec.ts)
- **Historical typing evidence:** a September 21 integration report records native input-to-paint samples of 15–36 ms while a suggestion request was deliberately delayed by two seconds. The report is explicitly historical, and the entry does not specify a long-note workload, so it cannot establish current large-note typing performance. [Integration report](../architecture/current-evidence-integration.md)
- **Some extension work is viewport bounded:** search highlight decorations scan `view.visibleRanges`, as do task date decorations. That limits those features' scan scope. [Search highlighting](../../src/lib/features/notepad/editor/searchHighlightExtension.ts), [Task date decorations](../../src/lib/features/notepad/editor/taskDateExtension.ts)
- **Other work still scales with the document:** Markdown decoration rebuilding runs on document changes and selection changes, walks the whole currently published syntax tree, and sorts the resulting decorations. Passive table detection scans all document lines and rebuilds on each document change. These are concrete profiling candidates for very long notes even when CodeMirror limits rendered DOM to a viewport; source inspection alone does not establish they are currently slow. [Markdown decorations](../../src/lib/features/notepad/markdown/markdownExtensions.ts), historical `passiveTableExtension.ts` (removed in `9d2644f4`; inspect that commit's parent)
- **Current component measurement:** `pnpm exec vitest bench src/lib/features/notepad/markdown/markdownDecorations.bench.ts --run` passed in this checkout. For its fully parsed 54,890-character, 500-section fixture, mean Markdown-decoration rebuild time was 1.9740 ms for one pane and 3.4602 ms for two sequential pane rebuilds. Passive-table inventory averaged 0.4340 ms; code-context extraction on a fresh document averaged 4.5042 ms, while the cached query was effectively negligible at this scale. These are Node microbenchmarks using a state-only stand-in for `EditorView`, not DOM layout, native WebKit, complete typing latency, save latency, or timings comparable to AFFiNE's renderer acknowledgement measurement. [Benchmark fixture](../../src/lib/features/notepad/markdown/markdownDecorations.bench.ts)
- **Incremental edits, full-text notification:** ordinary edits forward CodeMirror transactions into the per-note document and other attached panes. However, each content-changing dispatch invalidates a Markdown string cache and the change callback reads it, materializing the entire document as a string. Autosave is separately debounced by one second, so this full-text notification should not be confused with a disk write per keystroke. [Document runtime](../../src/lib/features/notepad/editor/editorDocumentRuntime.ts), [Autosave scheduling](../../src/lib/features/notepad/orchestration/persistenceController.ts)
- **History scale is a different workload:** the documented current-format scale fixtures use 64 KiB repetitive Markdown notes and up to 10,000 revisions for one hot note/100,000 revisions across a vault. Their history entry/paging/diff/restore budgets are not live editor keystroke measurements. An older native Editing Window spec selects 1 MiB notes but measures History Mode interactions, not sustained typing in those notes. [Scale documentation](../../e2e/README.md), [Editing Window history spec](../../e2e/specs/scale/editing-window-native-scale.spec.ts)

Assessment: Gneauxghts has useful bounded presentation evidence and a narrower Markdown workload than AFFiNE's problematic canvas/embedded-frame examples. Its remaining full-document extension scans mean it should not be described as immune to size-related editing cost. A fair comparison needs matched content, platform, release/build configuration, warm/cold conditions, and separate measurements of opening, sustained typing, scrolling and autosave; those matched results are not present in the inspected evidence.

## Follow-up: Gneauxghts edit-path design investigation

Investigated the two remaining document-wide paths after table support was removed from the current working tree. No production behavior was changed. A temporary Vitest diagnostic was run and removed; the observations below are component-level Node measurements, not mounted Chromium or native WebKit timings.

### Scaling probe

The fixture repeats this 80-character ASCII Markdown section to exactly 50,000, 500,000 and 2,000,000 characters:

```markdown
## Heading

Prose **bold** and [[Note|alias]] with ==highlight==.

- One
- Two

```

Each case constructed `EditorState` with the production `createMarkdownLanguage()`, fully parsed with `ensureSyntaxTree(state, doc.length, 10_000)`, and published parsing via `state.update({}).state`. Each timed operation had two warmups and seven measured samples; the table reports medians. Decoration rebuilding called the real `buildMarkdownDecorations({ state } as EditorView)` without a mounted DOM. Flattening called `toString()` once on each of nine distinct immutable text versions, created before timing by replacing one character near the middle. The Related input-key probe timed one `JSON.stringify(['/note.md', 'Title', doc])`; the current comparison constructs two such keys.

| Characters | Lines | Syntax nodes | Decorations | Decoration rebuild | Full-text string | One Related input key |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 50,000 | 4,376 | 13,751 | 8,750 | 3.354 ms | 0.067 ms | 0.029 ms |
| 500,000 | 43,751 | 137,501 | 87,500 | 34.323 ms | 0.331 ms | 0.303 ms |
| 2,000,000 | 175,001 | 550,001 | 350,000 | 141.638 ms | 1.538 ms | 1.278 ms |

A separate untimed syntax-tree iteration restricted to a 3,000-character interval near the middle visited 827, 826 and 826 nodes respectively. This establishes the reduced traversal scope available to a bounded implementation, not the latency or correctness of an implemented viewport decorator. The fixture is deliberately formatting-dense, fully parsed and warmed; these numbers must not be treated as normal-note typing latencies or extrapolated universally. Parsing, DOM/layout, complete callbacks, IPC and persistence were outside timing. Compared with full decoration rebuilding in this probe, string materialization is the smaller direct cost.

### Full-text callback: why it exists and a better boundary

`EditorDocumentRuntime` already keeps a persistent CodeMirror document but invalidates its string cache on a content-changing dispatch. `#notifyMarkdownChange` immediately reads `this.markdown`. `DocumentEditingService.recordUserEdit` then updates the authoritative open draft's string, advances operation state, updates empty-content behavior and invalidates derived views. Delaying that callback alone would leave draft state stale around persistence, publication, conflicts and retained chat context. [Runtime](../../src/lib/features/notepad/editor/editorDocumentRuntime.ts), [Document editing](../../src/lib/features/notepad/document/documentEditingService.ts), [Draft state](../../src/lib/features/notepad/document/documentState.ts)

Recommended direction: let the existing document boundary adopt a current immutable text value plus change/version information immediately, without requiring a string. Keep runtime history and per-pane selections where they are. Serialize a particular immutable text version lazily and cache that serialization when save capture, a search request, chat/context capture or another genuine string boundary requires it. CodeMirror `Text` already provides immutable tree storage, structural sharing and partial reads, so a new rope or retained unbounded edit log is unnecessary. Whether to expose `Text` directly or wrap it in a small document-body value is an implementation choice; wrapping is justified only if it centralizes snapshots/equality/empty-content semantics rather than scattering getters throughout callers. [CodeMirror Text reference](https://codemirror.net/docs/ref/#state.Text)

This needs a consumer audit: the current `Notepad.svelte` Related effect eagerly reads `working.markdown`, and `RelatedNotesStore.update` compares JSON-serialized full-text context keys. An immediate revision/identity notification should invalidate such consumers; they should capture the text when refreshing rather than read/serialize it merely to detect a change. Search already waits for its 120 ms debounce before obtaining current Markdown. Save capture must pin the specific immutable text/version before asynchronous work; an unbound callback that reads whichever text is current later would break existing save/adoption guarantees. [Related context effect](../../src/lib/features/notepad/Notepad.svelte), [Related store](../../src/lib/features/notepad/related/store.svelte.ts), [Search scheduling](../../src/lib/features/notepad/search/store.svelte.ts), [Save controller](../../src/lib/features/notepad/orchestration/persistenceController.ts)

Revision numbers can identify obsolete async results and invalidate caches, but cannot replace exact authored-content equality: undoing A → B → A must still become clean. Use structural/content equality at the document boundary and preserve existing save-result, conflict, metadata and publication semantics. Some equality cases can still require scanning; the goal is to remove unconditional full-string creation from every edit, not to claim every document operation becomes constant time.

### Formatting: bounded presentation before complex caching

The parser is already incremental; the expensive work found here is the consumer traversing the entire currently published tree, calling decorators, sorting and rebuilding all ranges. Selection changes do this to reveal Markdown syntax around the cursor. A global reparse is not required for that presentation change. [Markdown plugin](../../src/lib/features/notepad/markdown/markdownExtensions.ts), [Conceal predicates](../../src/lib/features/notepad/markdown/conceal.ts)

Recommended first step: rebuild visible presentation from `view.visibleRanges` and the syntax nodes intersecting those ranges, responding to document, viewport, selection and parser-publication changes. Inspect enclosing syntax nodes to preserve context, but bound per-line decoration emission to the drawn ranges. In particular, existing fenced-code and blockquote handlers loop over every line of an intersecting block; merely adding `from`/`to` to the outer tree traversal would retain that pathological cost for huge blocks. De-duplicate enclosing nodes across multiple visible ranges. Keep conceal/reveal decisions and atomic cursor behavior pane-local. Initial reveal must retain the existing viewport parse-and-layout settling contract. [Code decorators](../../src/lib/features/notepad/markdown/decorations/codeBlocks.ts), [Quote decorators](../../src/lib/features/notepad/markdown/decorations/blockquote.ts), [Presentation readiness](../../src/lib/features/notepad/editor/editorPresentation.ts), [CodeMirror decoration example](https://codemirror.net/examples/decoration/)

If bounded rebuilding still costs too much, separate selection-independent semantic ranges from the selection-dependent conceal projection, map cached ranges through transactions, and recompute affected syntax containers. A cursor move then revisits old/new affected constructs rather than the whole note. Invalidation must account for syntax changes beyond the typed characters (for example adding a code fence), as well as background parse publication; changed character offsets alone are insufficient. Do not begin by building a second Markdown parser or elaborate whole-document cache.

CodeMirror requires block widgets and replacements that cover line breaks to be provided directly, before viewport calculation. Those layout-structural decorations need their own incrementally maintained state field if introduced or encountered during this work; they cannot simply be moved into a viewport-dependent plugin. [Official decoration source constraints](https://codemirror.net/docs/ref/#view.EditorView.decorations)

Suggested implementation order is bounded Markdown presentation first, then the immutable draft/snapshot boundary and its eager consumers. Validation should include repeated cursor moves with a fixed viewport as offscreen content grows; edits introducing/removing distant-reaching syntax; very long fenced blocks and quotes; scrolling into previously unrendered content; two panes with different selections; and save capture followed by later edits, undo-to-baseline and external conflicts. A native typing/scrolling trace remains necessary to quantify the end-user improvement.
